## 一、总体结论：形式覆盖率高，能力闭环缺口大

### 1.1 结论摘要

代码层面"类目清单"基本齐了：Policy、ToolGateway、Approval、ActionLedger、Idempotency、DAGScheduler、GraphBuilder、ConditionalEdge、Checkpoint、HybridRetriever、Citation、RagEvaluator、MemoryManager、Metrics、BadCase、Trace 都有对应实现，类名与方案第三章的文件清单几乎一一对应。

但**方案要的不是类清单，而是可执行、可审计、可恢复、可评测的闭环**。按这个标准衡量：

| 模块 | 方案要求 | 现状 | 匹配度结论 |
|------|---------|------|-----------|
| 受限自治层 | Policy + Approval + Ledger 挡住所有高危写操作 | 代码齐全，但审批闭环不可达、审批接口无权限校验、默认策略对写工具是"放行"、租户校验 fail-open | ⚠️ 骨架达成，闭环不成立 |
| 确定性并行 DAG | 有界并行、失败传播、取消、确定性结果 | 有实现，批次屏障式并行 + 补偿顺序非逆拓扑 + 无 PENDING 兜底 | ⚠️ 可用但不满足"确定性/可恢复"表述 |
| LangGraph 条件边 + Checkpoint | 条件路由、循环上限、可恢复 | 有实现，但恢复语义是 no-op、循环上限只有全局 1000 步 | ❌ 恢复能力不成立 |
| 企业 RAG | 混合检索、引用、离线评测、可回归 | 组件齐全，但 BM25 无租户、无 Rerank、评测对"模拟答案"打分、真库 schema 冲突、未接入对话 | ❌ 演示级，不满足"可评测" |
| 持久化分层记忆 | 四层 + TTL + 隔离 + 脱敏 + 预算控制 | 四层/TTL/MySQL+Redis 有；KEYS 全库扫描、无清理调度、无预算控制、脱敏不全、管理接口无租户校验 | ⚠️ 存储达成，治理不达成 |
| ERP 状态机并发安全 | 显式迁移表 + 乐观锁 + 分布式锁 + 幂等 | 迁移表有且已接入 4 个 Service；但乐观锁被多处 Wrapper/原生 SQL 绕过；两套状态机并存；工作流校验的迁移与实际写入不一致 | ⚠️ 部分达成 |
| ERP 工具网关 | 所有 Tool 调用走网关 + 租户投影 + 审批 | 11 个只读工具已走网关；写工具 OrderActionTools 未接入 Chat → 无法被 AI 调用 | ⚠️ 只读达成，写工具未交付 |
| 操作型 Tool（1-2 个） | 受控写工具可被 AI 调用 | 类存在、单测通过，但 `ChatService` 未传入该 Bean，且审批链路不可能打通 | ❌ 交付物存在但不可用 |
| 多租户隔离 | 强制注入 + 查询过滤 + 审计 | 租户 ID 来自客户端 Header/参数，未与登录态绑定；无租户时工具层"查全部" | ❌ 未达成 |
| 评测闭环 | 100 条评测集 + 成功率看板 + Trace | 评测集 100 条有（迁移冲突）、Metrics 是进程内计数（重启清零）、Trace 双轨 | ⚠️ 部分达成 |

### 1.2 关键判断（按重要性）

1. **方案的核心承诺"受限自治"没有真正建立**：网关存在，但默认策略 OBSERVE 对写工具是放行、租户隔离缺省会查全库、审批闭环不可达、写路径（工作流/库存/OrderActionTools）绕过网关与审计。
2. **部署不可复现**：`db/migration` 下的 20+ 个 SQL 没有任何自动执行机制（无 Flyway/Liquibase，无 `spring.sql.init`，迁移指南只覆盖 version 列），且其中两个迁移脚本在按序号执行的干净库上必然失败（`agent_rag_evaluation` 表定义冲突）。
3. **应用启动强依赖 PostgreSQL**：`PgVectorManualConfig` 手动创建的 `PgVectorStore` 是饿汉 Bean，`afterPropertiesSet()` 会执行 `CREATE EXTENSION`/建表，PG 不可用则 Spring 上下文启动失败 —— 方案文档里的"三级降级到 MySQL/BM25"在本工程中到不了，因为根本起不来。
4. **PaiAgent 未按方案投入**：HTML 把 PaiAgent 定为"主项目（35% 投入）"，但 `D:\AAA.idea.code\PaiAgent` 源码最后修改时间为 2026-09-03，本次魔改（10-10 ~ 10-13）零改动；方案里的 DAG/Graph/记忆/RAG 能力已在 erp-api 内平行重写了一套，与"不要重写平台、保留 PaiAgent 编排能力"的决策相反。
5. **测试不可在干净环境复现**：14 个测试文件硬编码 `127.0.0.1:3306` + `root/1234` 并直接读写业务库；无任何 `@SpringBootTest`，Spring 上下文/Bean 装配从未被验证。
6. **交付报告数字与事实不符**：commit 声称"全量测试 225/225"，`full_test.log` 实际 219；方案分析称"11 个 @Tool 类、40 个只读方法"，实测 12 个类、15 个 `@Tool` 方法（含 2 个写工具）；称"6 个定时扫描、4 个已实现"，仓库中业务 `@Scheduled` 只有 3 处（SSE 心跳 + MessageScheduler ×2）。

## 二、P0 致命问题

### P0-1 租户隔离是"客户端说了算"的假隔离（水平越权）

- `TenantInterceptor.preHandle()` 直接从 `X-Tenant-Id` 请求头或 `merchantId` 参数取租户并写入 ThreadLocal（`TenantInterceptor.java:36-61`），信息来源完全由调用方控制，未与登录用户/门店绑定；"从 Spring Security 上下文获取"仍是 TODO 注释（同文件 63-70）。
- 取不到租户时既不拒绝也不清理，直接 `return true`（`TenantInterceptor.java:72-74`）。
- `ToolGateway` 对缺租户显式 fail-open：只 `log.warn` 后继续执行，注释写明"工具层按无租户处理（查全部）"（`ToolGateway.java:129-133`）。
- 全部 AI Tool 采用 `if (merchantId != null) wrapper.eq(...merchantId)` 模式（如 `OrderTools.java:36-39`、`OrderActionTools.java:56-68` 等 12 个类全部如此）→ **不传 `X-Tenant-Id` 即可查询全租户订单**（含收件人姓名、手机、地址）。
- agent 侧所有 REST 管理接口都以请求参数 `merchantId` 为准，无一处用 `TenantContext`/登录态校验：
  - `MemoryController`：store/retrieve/delete/list/clear 均可指定任意 merchantId 读写删记忆（`MemoryController.java:39-157`）；
  - `ApprovalController`：`listPending(merchantId)`、`approve/reject` 的 `approverId` 也来自请求参数 → 可批准他人审批、可伪造审批人（`ApprovalController.java:33-86`）；
  - `TraceController`：`/recent?merchantId=` 任意商户 trace（`TraceController.java:39-48`）；`/chain/{traceId}` 无任何租户校验（26-34）；
  - `RagController`：检索/评测/历史均可传任意 merchantId（`RagController.java:41-49, 366-379`）；
  - `WorkflowController`：`merchantId` 取请求体，缺省 `1L`，直接驱动售后写流程（`WorkflowController.java:36-45`）；
  - `ActionLedgerController` / `BadCaseController` 同模式。
- 会话越权：`AiConversationHistoryServiceImpl.getConversation(sessionId)` 只按 sessionId 过滤（`AiConversationHistoryServiceImpl.java:20-25`），`ChatController.getHistory` 不校验归属（`ChatController.java:45-49`）→ 拿到 sessionId 即可读他人对话。

### P0-2 PgVector 让应用启动强依赖 PostgreSQL，降级叙事不成立

- `PgVectorManualConfig.pgVectorStore(...)` 在启动时创建 `PgVectorStore`，且 `.initializeSchema(true)`（`PgVectorManualConfig.java:27-44`）。
- Spring AI `PgVectorStore implements InitializingBean`，`afterPropertiesSet()` 会执行 `schemaValidator.validateTableSchema(...)`（默认关闭）以及 `CREATE EXTENSION IF NOT EXISTS vector/hstore` + 建表（spring-ai-pgvector-store 源码 403-446 行）。
- 结果：PostgreSQL/pgvector 未部署 → Bean 初始化抛异常 → **整个 Spring 上下文启动失败**。方案里"PGVector 部署困难 → MySQL FULLTEXT → 纯 BM25"的三级降级在真实部署中永远走不到第二级。
- PG 账号密码硬编码在代码里（`PgVectorManualConfig.java:32-35`），并重复在 `application-agent.yml:49-51, 96-100`。

### P0-3 数据库迁移无法在干净环境重建（按序执行会直接失败）

- 仓库没有任何迁移执行器：根 pom / erp-api pom 无 flyway/liquibase；无 `spring.sql.init`；`docs/数据库迁移执行指南.md` 只讲 `docs/sql/migration_v4.1.1_add_version_columns.sql`。`erp-api/src/main/resources/db/migration` 下 20+ 个 V1_xx 脚本只能靠人工执行。
- `agent_rag_evaluation` 三套定义冲突：
  - V1_11_0 先建表：列为 `query / expected_chunks / category / tags`，**没有** `merchant_id / question / relevant_chunks / domain`；
  - V1_16_0 再 `CREATE TABLE IF NOT EXISTS`（静默失效，不会补列）；
  - V1_16_1、V1_22_0 却按 `merchant_id, question, expected_answer, relevant_chunks, domain, difficulty` 插入 → **按序执行必然 Unknown column**；
  - 运行期 `RagEvaluator.loadEvaluationCases` 同样查询 `merchant_id/question/relevant_chunks/domain`（`RagEvaluator.java:431-457`）→ 真库上报 SQL 异常，每日 2 点评测任务会以"失败"结束。
- `agent_memory` 两套定义冲突：V1_13_0（`id` 自增主键 + `memory_id` 唯一键 + `merchant_id NOT NULL`）与 V1_17_0（`memory_id` 主键、字段可空）语义不同，后者静默失效；`merchant_id NOT NULL` 与代码里允许 merchantId 为 null 的路径冲突。
- 死表：`V1_12_0` 的 `agent_document / agent_knowledge_chunk / agent_bm25_index / agent_knowledge_stats`、`V1_13_0` 的 `agent_memory_snapshot / agent_memory_access_log / agent_sensitive_mask_log / agent_memory_stats`、`V1_21_0` 的 `agent_tool_policy` 全部没有被任何 Java 代码引用。

### P0-4 人工审批闭环不可达（"受控写工具"实际上是死代码）

- `ChatService` 硬编码 `toolContext.put("approved", false)`（`ChatService.java:153`），全仓库没有任何地方放入 `approved=true`。
- traceId 每次对话新生成（`ChatService.java:147`），审批匹配键是 `(traceId, toolName)`（`ApprovalService.java:136-145`）→ 用户"批准后重发"仍是新 traceId，永远匹配不上；每次重发都会再创建一条 PENDING 审批（`ApprovalService.createApproval` 无去重，55-73）。
- 写工具根本没有进入对话链路：`ChatService.java:157` 传给 ChatClient 的 12 个参数里没有 `OrderActionTools`；全仓除单测外无引用 → "1-2 个受控写工具"无法被 AI 调用。
- `ApprovalController.getById` 实现错误：用 `approvalService.listByTraceId("")` 再按 id 过滤（`ApprovalController.java:94-96`）→ 永远返回 404。
- `expireOldApprovals()` 定义了但无任何 `@Scheduled` 调用（`ApprovalService.java:186-201`）→ 5 分钟超时形同虚设，PENDING 记录永久堆积。
- `markFailed` 把状态改回 PENDING 却保留 `approverId/approvedAt`（`ApprovalService.java:125-131`）。
- `approve/reject` 是"读-改-写"无事务、无状态条件更新（78-108）→ 并发审批存在覆盖竞态。

### P0-5 网关并发保护的锁释放逻辑有错

- `ToolGateway.execute` 的 finally 里无条件 `executionLocks.remove(toolName)`（`ToolGateway.java:310-321`）。
- 场景：`allowConcurrent=false` 的工具正在执行（持内存锁）→ 第二个调用者 `acquireLock` 失败抛异常 → finally 把第一个调用者的锁删掉 → 第三个调用者成功加锁，与第一个**并发执行**。本该串行化的工具在并发下失去互斥。

### P0-6 幂等实现不满足"幂等"语义

- `IdempotencyGuard.checkAndMark` 是 `GET` 后 `SET` 两步（`IdempotencyGuard.java:50-69`），非原子；两个并发同参请求可以同时通过检查 → 重复下单/重复退款风险（正是方案要防的场景）。
- Redis 不可用时没有降级：`IdempotencyGuard`/`DistributedLockService` 内部不捕获 Redis/Redisson 异常（`IdempotencyGuard.java:52-67`；`DistributedLockService.java:47-63` 只捕获 `InterruptedException`）→ 工具直接失败；`ToolGateway` 注释里的"Redis 不可用自动降级为内存锁"只在 Bean 缺失时成立。
- 幂等键用 `args.toString()` 拼接（`IdempotentKeyGenerator.java:37-44`），对 Map/数组/自定义对象不稳定；`idempotencyKey` 也不含 traceId，24h 内"参数相同的两次合法操作"会被误判为重复（TTL 见 26 行）。
- 命中重复时返回的是拼接字符串而不是真实结果（`ToolGateway.java:146-148`），调用方拿到的是"伪成功"文本。
- `LockHandle implements AutoCloseable` 但 `close()` 是空实现（`DistributedLockService.java:144-147`），try-with-resources 会静默泄漏锁直到 TTL；`tryLock` 用固定 leaseTime、无 watchdog（51 行），长任务超时后锁提前释放。

### P0-7 写操作绕过网关与审计（方案要求"所有写操作有审计"）

- `AgentWorkflowService` 直接 `shopRefundMapper.update(...)` / `shopOrderMapper.update(...)`（`AgentWorkflowService.java:239-242, 272-275`）：不经 Policy、不写 ActionLedger、不校验租户、不做幂等；节点 `audit_log` 只是 `log.info`（305-315），`notify_customer` 也只是日志（294-302）——"通知已发送"是假的。
- `OrderActionTools` 直接 `orderService.updateById(...)`（`OrderActionTools.java:70-73, 124-127`）：网关审计只在被网关调用时产生，工具本身不落审计。
- `OGoodsInventoryServiceImpl.deductStock/addStock/lockStock`（`OGoodsInventoryServiceImpl.java:62-121`）无审计、无租户校验。

## 三、P1 高风险问题

### P1-1 状态机与业务实际行为不一致

- 工作流 `validate_transition` 校验的是"订单当前状态 → 3（已完成）"（`AgentWorkflowService.java:219-228`），但 `OrderStateMachine` 只允许 `2→3`、`101→2`、`12→3`（`OrderStateMachine.java:55-62`）；起始状态 0/1/21 的订单直接失败 → 该工作流对绝大多数订单不可用。
- 工作流全程**没有更新订单状态**（只改退款状态 + 追加 sellerMemo）→ 校验的那次迁移从未发生；`process_refund` 直接 `set(status, 3)` 也不经 `RefundStateMachine`（239-242）。
- 同一 (orderId, refundId) 重复执行会在 sellerMemo 上反复追加 `[AI售后处理] 已自动处理退款流程`（270-271），无幂等。
- 两套状态机并存：`cn.qihangerp.statemachine`（在用）与 `cn.qihangerp.service.statemachine`（`OrderState.java/OrderStateMachine.java/RefundState.java/RefundStateMachine.java/TransitionValidator.java/OrderStatusUpdateService.java` 等 7 个类）仅被测试引用 → 重复实现、语义分叉。
- `recordAdministrativeRefundTransition` 对管理型迁移"只记录不校验"（`TransitionValidator.java:79-92`），等于保留了绕过强约束的口子。
- 状态迁移事件在"校验时"发布（`TransitionValidator.java:36-47`），监听器用 `REQUIRES_NEW` 独立落库（`StateTransitionTraceListener.java:34-36`）→ 业务后续更新失败/回滚时，Trace 里仍会留下一条"迁移成功"的记录。
- `ShopRefundServiceImpl` 允许 `oldStatus == null` 时设置任意状态（`ShopRefundServiceImpl.java:99-104`），并在非法迁移时"再调一次 validator 只为发事件"（105-121），逻辑绕。

### P1-2 乐观锁被多处绕过，version 只是装饰

- `V1_19_0` 给 `oms_shop_order / oms_shop_refund / o_goods_inventory / erp_purchase_order` 加 version，但 `ErpPurchaseOrder` 实体没有 `@Version` 字段 → 迁移与代码不匹配。
- MyBatis-Plus 乐观锁只在 `updateById(entity)` 且实体带 version 时生效。以下路径全部绕过：
  - `OGoodsInventoryMapper.deductStockAtomic/addStockAtomic` 原生 SQL（`OGoodsInventoryMapper.java:24-37`）不校验也不递增 version；
  - `AgentWorkflowService` 两处 `LambdaUpdateWrapper`（239-242、272-275）；
  - `OrderActionTools` new 出仅含 id+字段的实体 `updateById`，version=null（`OrderActionTools.java:70-73, 124-127`）；
  - `OGoodsInventoryServiceImpl.lockStock` 先读快照再 `updateById`（104-115），version 未回填 → 并发下锁定量/可用量丢失更新。
- 混用"乐观锁更新"与"原生 SQL 更新"且不维护 version，会让乐观锁在并发下给出错误的安全感。

### P1-3 库存扣减不变量被破坏

- `deductStockAtomic` 只校验 `quantity >= n`，不校验 `available_quantity >= n`（`OGoodsInventoryMapper.java:24-28`）：当存在锁定量（locked>0）时，可用量会被扣成负数。
- 原子 SQL 不更新 `update_time / stock_status / version`（同上），与实体语义不一致；按 update_time/version 做增量同步的调用方会漏数据。
- `lockStock` 对 `lockQuantity/availableQuantity` 为 null 无保护（`OGoodsInventoryServiceImpl.java:107-109`）。
- `writeOperation` 把 `bizType=4、bizId=0、bizNum=""、price=0` 全部写死（126-149）→ 流水无法关联业务单据，"可追溯"打折。
- 扣减/加锁不判断 `is_delete`，已删除库存仍可被操作。

### P1-4 RAG：租户、召回、评测三处都有硬伤

- BM25 完全不做租户过滤（`HybridRetriever.java:129-139` 明确 TODO）；`KnowledgeLoader` 启动时把 `rag_document` 全表灌进共享内存索引（`KnowledgeLoader.java:29-46`）→ 多商户知识互相可见；`RagController./index` 可运行时追加任意 chunk（`RagController.java:117-130`），无租户无权限 → 索引投毒。
- BM25 索引用 `HashMap`（`BM25Retriever.java:43` 附近）非线程安全；运行时索引与并发检索可触发 `ConcurrentModificationException`。
- `HybridRetriever` 注释说"并行执行 BM25 与向量"（70-72），实际是串行调用；MySQL FULLTEXT 结果被包装成"向量结果"（`MysqlFullTextRetriever.java:66`），RRF 里 vectorScore 语义混入 BM25 相关度；融合时先放向量结果、BM25 只补充缺失项（`HybridRetriever.java:158-179`）→ 同时命中的 chunk 会丢失 bm25Score。
- PgVector 是"先取 topK*2 再按 metadata 过滤"（`PgVectorRetriever.java:76-93`），过滤后可能不足 topK；且 `merchant_id` 缺失的文档对所有租户放行（81 行 `mid == null ||`）。
- 无 Rerank 实现：`application-agent.yml` 的 `spring.ai.rag.rerank.*` 与 `agent.rag.rerank-enabled` 无任何消费者。
- 评测对"模拟答案"打分：`generateAnswer` 只是拼接前 3 个 chunk（`RagEvaluator.java:412-426`），`calculateBLEU/ROUGE` 都是同一个 Jaccard（398-406），文本相似度用 `split("\\s+")`（323-334）→ 中文几乎恒退化为整串比较，answer/faithfulness 这类指标不可用。
- `relevant_chunks` 用 `replace("[","").replace("]","").split(",")` 解析 JSON（437-451），格式稍变即静默产生错误集合。
- `RagController` 多处 `request.get("merchantId").toString()` 直接 NPE（45、73、95、232、367）；`topK` 用 `(Integer)` 强转。
- RAG 未接入对话：ChatClient 工具列表里没有检索/引用工具，`CitationGenerator` 只被 REST 接口使用 → "答案带引用"在产品链路不可达。
- `RagEvaluationScheduler` 的日志用 SLF4J 不支持的格式占位符 `{:.2f}` / `{:.4f}`（45-50、54 行）→ 输出为字面量 + 参数错位，监控日志不可读。

### P1-5 分层记忆：存储有了，治理没有

- `MemoryManager.listKeys` 对 SESSION/USER/TEAM 用 `redisTemplate.keys(pattern)`（`MemoryManager.java:150-157`），而 `ChatService.buildMemoryContext` 每条消息调用 3 次（`ChatService.java:76-97`）→ 生产环境 KEYS 阻塞 Redis。
- 记忆上下文无预算：把 TEAM/USER/SESSION 的**所有**键值原样拼进 SystemMessage（`ChatService.java:71-101, 133`），与方案"上下文预算控制器（摘要/截断/按需加载）"完全相反；`saveSessionMemory` 每轮写一个新 key（107-115）→ 无上限增长。
- WORKING 层内存 map 无淘汰；`cleanupExpiredMemories()` 只被手动 REST 触发（`MemoryController.java:174-182`），无定时任务 → 无界增长；`agent_memory` 过期行同样只靠手动清理。
- `delete()`/`clearScope()` 不校验租户（`MemoryManager.java:121-137, 163-169`），配合 P0-1 可删他人记忆。
- 脱敏不全：`autoMask` 未包含姓名（`SensitiveDataMasker.java:95-109`，与类注释不符）；15 位身份证漏脱敏（正则只有 18 位，25 行）；`maskChineseName` 的正则会匹配整句并替换成"我***"（28、83-88 行）；ChatService 存的是原始问答文本（含地址/订单信息），只做 4 类正则。
- `access_count/last_accessed_at` 只改内存对象、从不回写（`MemoryEntry.java:127-133`）→ 淘汰/衰减策略没有数据基础。

- "扣减与流水同事务"的断言并没有真的验证事务：`testServiceDeductWritesFlowLog` 直接 new ServiceImpl 调方法，没有 Spring 事务代理（`InventoryConcurrencyTest.java:233-255`）。

### P1-7 监控/评测闭环名不副实

- `MetricsCollector` 是纯进程内 `LongAdder`（`MetricsCollector.java:28-113`），无 Micrometer/Prometheus 注册，重启清零、多实例各算各的；类注释声称 P50/P95/P99（17 行）但代码只有 min/max/avg（148-177）。

## 四、P2 中风险问题

### P2-1 PolicyRegistry 启动扫描健壮性

- `@PostConstruct` 中对所有 `beanDefinitionNames` 调 `applicationContext.getBean(beanName)`（`PolicyRegistry.java:45-85`）→ 提前实例化全部 Bean（含懒加载/重依赖），可能改变启动顺序、触发循环依赖或初始化副作用；异常只用 `log.debug` 吞掉（81-84）→ 策略漏注册无告警。
- 用 `bean.getClass().getDeclaredMethods()` + `method.getAnnotations()` 直读注解，未用 `ClassUtils.getUserClass`/`AopUtils.getMostSpecificMethod`（与 `GatewayToolCallbackFactory.java:70` 的做法不一致）→ 一旦工具 Bean 被 CGLIB 代理，`@Tool/@ToolPolicy` 可能读不到。
- 缺策略时默认 OBSERVE（`ToolGateway.java:445-446, 478-524`），而 `validatePolicy` 只在 `level.allowsWrite()` 时校验写权限（358-375）→ **未标注策略的写工具会被直接执行**，与"默认安全"的注释相反。
- 注册键是 `SimpleClassName.methodName`（`PolicyRegistry.java:63`），而模型看到的工具名可能是 `@Tool(name=...)`（`GatewayToolCallbackFactory.java:75-78`）→ 自定义工具名会导致策略/审计/审批名字错位。
- `AutonomyLevel` 的 SUGGEST/DRAFT 在执行层没有任何语义（`ToolGateway.java:135-198` 只处理 EXECUTE 的幂等与 ESCALATE 的审批）；DRAFT 级工具会直接执行真实写操作且跳过写权限校验。

### P2-2 策略字段形同虚设

- `maxBatchSize` 依赖 `ToolExecutionContext.batchSize`，但全仓无 `setBatchSize` 调用 → 永远为 1，限制无效。
- `timeoutSeconds` 只被读取和透传，没有任何执行超时包装。
- `requiresTenantIsolation` 的唯一作用是"merchantId 为空时 log.warn"。
- `agent_tool_policy` 表（含 is_idempotent/requires_approval/enabled 等列）没有实体、Mapper、加载逻辑 → 表在，动态策略能力不在。

### P2-3 审计数据不完整

- `ActionLedgerRequest.approved` 从未在 `ToolGateway.recordAuditLog` 中赋值（`ToolGateway.java:399-419`）→ `agent_action_ledger.approved` 永远是 NULL，`ActionLedgerService.getApprovalActions(approved=true/false)` 永远查不到数据（`ActionLedgerService.java:151-169`）。
- 失败分支重新反射读 `@ToolPolicy`（`ToolGateway.java:277-293`），与主流程使用的 PolicyRegistry 策略来源不一致 → 可能漏审计。
- 审计是同步单条 insert（方案要求"异步队列 + 每 500ms/100 条批量刷盘"），且审计失败静默（`ActionLedgerService.java:65-70`）。
- `input_params` 直接序列化工具入参，敏感字段（手机号/身份证/地址）会明文入库，绕过记忆层脱敏。

### P2-4 DAG/图引擎细节缺陷

- 调度是"批次屏障"：收集 ready 节点 → 全部 join 后才进入下一轮（`DAGScheduler.java:104-119`）→ 无法流水线重叠，长尾节点拖慢整批。
- 补偿用 `nodeMap.values()` 反转（172-175），不是逆拓扑序；任何失败都会回滚**所有**成功且带 compensator 的节点（含无关独立分支）。
- 无 PENDING 兜底：若节点依赖一个不存在的 id，`readyNodes` 为空 → `break`（92-102），结果里遗留 PENDING，而 `hasFailures()` 为 false → `WorkflowResult.success=true` 但实际未全执行。
- `DAGScheduler` 在 `AgentWorkflowService` 构造时 new 一个共享实例（`AgentWorkflowService.java:68`），无 `@PreDestroy` → 线程池随容器关闭泄漏；`maxParallelism` 是全局共享而非每工作流。
- `GraphBuilder.execute` 的 executionId 用 `System.currentTimeMillis()`（`GraphBuilder.java:106`）→ 同毫秒并发执行 ID 冲突（checkpoint 唯一键含 executionId）。
- checkpoint 间隔 `steps % interval == 0`（133 行）在 steps 自增时机上 off-by-one；保存的 "currentNodeId" 实际是"刚执行完的节点"（120-124）。
- `resumeWorkflow` 是 no-op：只有 execute 全部结束后才保存快照（`AgentWorkflowService.java:108, 138`），快照里节点均为终态 → `DAGScheduler.execute` 的 while 条件立即为假，不重跑任何节点；中断场景根本没有快照。
- `saveCheckpoint` 用 `MAX(version)+1` 先查后插（`CheckpointManager.java:47-73`）→ 同一 execution 并发保存触发唯一键冲突。
- `StateSerializer.deserializeMap` 用裸 `Map.class`（`StateSerializer.java:75-82`）→ 类型契约被绕过，嵌套 JSON 得到 LinkedHashMap，后续 `(String)` 强转有风险。
- `ConditionalEdge.route` 无匹配且无 default 返回 null（`ConditionalEdge.java:44-51`），`GraphBuilder` 把 null 当"正常结束"而不报错（138-149）。
- 循环上限只有全局 `maxSteps=1000`（110 行），节点级 `maxIterations/stopCondition` 未实现（方案要求）。

### P2-5 接口层健壮性

- `WorkflowController` / `RagController` 用 `Map.of(...)` 组装响应（`WorkflowController.java:46-51, 60-64, 73-77`）：出现 null 值会 NPE 并返回 500；`resumeWorkflow/getStatus` 的 `IllegalArgumentException` 无统一异常处理。
- `MemoryController` 的 `MemoryLayer.valueOf(layer)` 非法值抛 IllegalArgumentException → 500；`store` 不校验 key/value，value 为 null 时写入 NOT NULL 列会异常。
- `ChatController.errorEmitter` 手工拼 JSON 未转义（`ChatController.java:63-71`）。
- SSE 流无 onTimeout/onError 取消：客户端断开后仍继续跑完 LLM（`ChatService.java:161-190`）；`sendJsonEvent` 吞掉 IOException（199-210），前端可能永远等不到 done。
- `GatewayToolCallback.parseArgs` 自行解析 JSON 并按参数名反射注入（`GatewayToolCallback.java:111-132`），依赖 `-parameters` 编译开关；缺参/类型不符时直接把 null 传给方法（基本类型即 IllegalArgumentException），且不支持 Spring AI 的 `ToolContext` 注入参数（当前工具未用，属潜在坑）。
- `GatewayToolCallback.call(String)`（无上下文重载）会走空 ToolContext（57-59 行），merchantId/traceId 为空 → 直接返回"工具执行异常"，该重载实际不可用。

### P2-6 缓存与其他

- `GoodsCacheService.searchGoods/searchSku` 在 merchantId 为 null 时用 `"public"` 桶（`GoodsCacheService.java:68, 102`），而底层查询在 merchantId 为 null 时不加租户过滤 → 全租户结果被缓存并复用；null 结果不缓存（穿透风险）。
- `evictAllSearchCache` 用 `KEYS`（201-202 行）→ 阻塞 Redis；`evictGoodsCache` 不清 SKU/搜索缓存（188-195），只靠 TTL。
- `common/R.java` 由整文件注释状态改为启用（commit ba491ef2），目前只有 `BadCaseController.getStats` 使用；同一模块已有 `AjaxResult/ResultVo` → 第三套响应模型。
- 硬编码凭据已入库：`application.yml:44`（DeepSeek key）、`application-agent.yml:26,41`（DashScope key）、PG/MySQL 口令。
- `TenantContext.setTenantId(null)` 只 warn 不清理旧值（`TenantContext.java:27-34`），线程复用场景有残留风险。
- `RedissonConfig` 手写字符串解析超时（68-87 行），对 `"6000ms"` 可用，但对 Spring Boot 常见的 `PT6S`/`6s` 之外格式回退默认值，配置歧义。

## 六、建议修复顺序（按性价比）

1. **先让系统能启动、能复现**：抽出 `agent.vector-store.enabled` 开关 + `@ConditionalOnProperty` 惰性化 PgVector；把 `db/migration` 接入 Flyway（或合并为一份权威 DDL）；把 14 个连真实库的测试改为 Testcontainers/H2 或 `@Tag("it")` 隔离。
2. **堵住越权**：`TenantContext` 只允许来自登录态（JWT/门店归属），禁止请求头直供；无租户时对需要隔离的工具**拒绝执行**而非放行；所有 agent 管理接口从登录态取 merchantId，删除请求参数通道。
3. **打通审批闭环或明确关闭**：统一 traceId 生命周期（会话级）、`ChatService` 注入 OrderActionTools、修复 `ApprovalController.getById`、给审批加 `@Scheduled` 过期与条件更新、把 `approved` 落到 ledger。
4. **修网关正确性**：锁释放加持有标记、幂等改 `SET NX` + 结果缓存、默认策略改"拒绝"、DRAFT/SUGGEST 补语义或从枚举移除、PolicyRegistry 用 AOP 安全的方式取注解。
5. **写路径归口**：工作流/库存/OrderActionTools 的写操作统一经过 Gateway（或至少写 ActionLedger + 状态机 + 幂等）。
6. **再谈评测与记忆**：RAG 评测先接真实 LLM 或明确标注"检索指标 only"；BM25 加租户维度；记忆 listKeys 改 `SCAN`/`HSCAN`，加定时清理与预算控制。
