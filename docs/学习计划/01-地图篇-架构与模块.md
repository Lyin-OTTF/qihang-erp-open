## 1. 一句话定位（面试开场就用这句）

> "启航 ERP 是一个 Spring Boot 单体多模块的电商业务中台：上游提供订单、商品、采购、库存、发货的进销存底座；
> 我在它上面补了一层 **可管控、可审计、可评测的 AI Agent 运行时**，并重构了库存一致性与订单状态机。"

三个关键词：**单体多模块**、**进销存底座**、**Agent 运行时治理**。

不要把它说成"微服务"——它是单体，这是事实，也是你后续讲"为什么单体更合适"的伏笔。

## 2. 三个时代：这个仓库是怎么长成现在的样子的

看 git 历史不要按提交逐个看，按"时代"看。整个仓库 704 次提交，可以切成三段：

| 时代 | 时间 | 代表提交 | 干了什么 |
|------|------|----------|----------|
| ① 上游业务底座 | 2024.01 - 2026.09 | `初始化项目` … `优化个人中心资料修改` | 电商进销存主流程、JWT+RBAC、Vue3 前端、7 个平台 SDK |
| ② AI 魔改（Week1-10） | 2026.10.10 - 10.13 | `f13521c1` 状态机与乐观锁 → `7597cf34` 可信执行边界 → `2d179a8c` RAG → `9a061589` 记忆 → `ba491ef2` 全量加固 → `def9537d` 完善 | 工具网关、五级自治、审批、审计、RAG、记忆、DAG、Trace |
| ③ 生产化收口 | 2026.10.14 - 10.17 | `a5cc4208` 评议修复 → `4278c643` 技术债 → `0c3ec521` 密钥外置 → `2e8d5ef2` 生产化 → `2e8342c0` 真实评测 | 修 P0、接 Actuator、Flyway、真实 LLM 评测、CI |

### 为什么这个顺序是合理的（面试可讲）

1. **先有业务，再有 AI**：没有订单/库存/售后的领域模型，Tool 没有可调用的东西。
2. **先有边界，再有智能**：Agent 能写库之前，必须先有策略、审批、审计——否则是"给猴子一把手术刀"。
3. **先有评测，再谈优化**：RAG 没有 Recall/MRR 就无法判断改动是好是坏。
4. **最后才做生产化**：可观测性、密钥、迁移、CI 是"能上线"的门槛，不是"能演示"的门槛。

> 面试话术：
> "我不是一开始就堆功能。第一周先做状态机和乐观锁，因为这是所有写操作的地基；
> 第二周做网关和审计，因为 AI 一旦能写库，必须有刹车；
> 第三周才做 RAG 和记忆；最后两周全部用来修前三周欠的债。"

## 3. 七个模块：谁依赖谁，为什么这么分

根 `pom.xml`：

```xml
<modules>
    <module>erp-api</module>   <!-- 启动模块：Controller + Agent 运行时 + 配置 -->
    <module>security</module>  <!-- JWT、登录、RBAC、SecurityConfig -->
    <module>common</module>    <!-- 通用返回体、异常、工具类、枚举 -->
    <module>mapper</module>    <!-- MyBatis-Plus Mapper 接口 -->
    <module>model</module>     <!-- 实体、DTO、VO、BO、Query -->
    <module>service</module>   <!-- 业务实现：订单/库存/采购/售后/状态机 -->
    <module>open-sdk</module>  <!-- 7 个电商平台 SDK 适配 -->
</modules>
```

### 3.1 依赖方向（必须背下来）

```
                 ┌──────────────┐
                 │   erp-api    │  启动类、Controller、Agent 运行时
                 └──────┬───────┘
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   ┌─────────┐    ┌──────────┐    ┌─────────┐
   │ service │    │ security │    │ open-sdk│
   └────┬────┘    └────┬─────┘    └────┬────┘
        ▼              ▼               ▼
   ┌─────────┐    ┌─────────┐    ┌─────────┐
   │ mapper  │    │ common  │    │ common  │
   └────┬────┘    └─────────┘    └─────────┘
        ▼
   ┌─────────┐
   │  model  │
   └─────────┘
```

三条铁律：

- **`service` 不依赖 `erp-api`**。所以状态机（`cn.qihangerp.statemachine`）放在 `service` 里，
  而不是放在 `erp-api/agent` 下——这样订单服务更新状态时可以直接调用，不需要反向依赖。
  这是"状态机下沉"这个提交（`def9537d`）的真正含义。
- **`model` 被所有层依赖**，所以它只能放数据结构，不能放业务逻辑（`InventoryChangeCommand.validate()` 是唯一的例外，属于自校验）。
- **`erp-api` 是唯一可启动模块**，所有 `@Configuration`、`@RestController`、`@Component`（Agent 相关）都在这里。

### 3.2 各模块职责与代码量（面试报数字要准）

| 模块 | Java 文件数 | 职责 | 面试要不要展开 |
|------|------------|------|----------------|
| `common` | 106 | `R<T>`/`AjaxResult`/`ResultVo`、异常、常量、工具 | 只需知道"有三套返回体"这个历史债 |
| `model` | 314 | 实体（`@TableName`）、BO/DTO/VO/Query | 只读 5 个核心实体 |
| `mapper` | 104 | MyBatis-Plus `BaseMapper` + 少量 `@Update` 原子 SQL | 精读 `OGoodsInventoryMapper` |
| `service` | 198 | 业务实现 + 状态机 | 精读库存/入库/出库/对账 |
| `security` | 19 | JWT 过滤器、`SecurityConfig`、`LoginUser`、RBAC | 精读 JWT 过滤器 |
| `open-sdk` | 251 | 淘宝/京东/拼多多/抖店/快手/微信小店/小红书 | **不读**，知道是适配器层 |
| `erp-api` | 187 | Controller、Agent 运行时（75 个类）、配置 | 精读 Agent 的 15 个类 |

合计 **1179 个 Java 文件**。这个数字面试时可以说，但要补一句：
"真正承载核心逻辑的不到 60 个类，其余是平台适配和 CRUD。"

## 4. 一次请求怎么走：以"查询订单列表"为例

### 4.1 链路

```
浏览器 (Vue3)
  │  Authorization: Bearer <jwt>
  ▼
JwtAuthenticationTokenFilter        ← security 模块
  │  解析 token → LoginUser → SecurityContext
  ▼
SecurityConfig 授权规则             ← anyRequest().authenticated()
  ▼
TenantInterceptor                   ← 从登录态取 merchantId 写入 ThreadLocal
  ▼
ShopOrderController                 ← erp-api/controller/oms
  ▼
ShopOrderService / ServiceImpl      ← service 模块
  ▼
ShopOrderMapper (BaseMapper)        ← mapper 模块
  ▼
MySQL oms_shop_order
```

### 4.2 关键代码：JWT 过滤器（`security/.../JwtAuthenticationTokenFilter.java`）

```java
if (request.getRequestURI().equals("/login")
        || url.contains("/login")
        || url.contains("/captchaImage")
        || url.contains("/order/get_detail")
        // ... 省略
        || url.startsWith("/actuator/health")
        || url.startsWith("/actuator/prometheus")) {
    chain.doFilter(request, response);   // 白名单：直接放行
    return;
}
LoginUser loginUser = tokenService.getLoginUser(request);
if (loginUser != null) {
    tokenService.verifyToken(loginUser); // 续期
    UsernamePasswordAuthenticationToken authenticationToken =
            new UsernamePasswordAuthenticationToken(loginUser, null, loginUser.getAuthorities());
    SecurityContextHolder.getContext().setAuthentication(authenticationToken);
} else {
    fallback(" 授权过期！", response);    // 注意：这里直接返回 JSON，不再往下走
    return;
}
chain.doFilter(request, response);
```

**这里有一个非常值得讲的坑（事故库第 11 条）**：
`SecurityConfig` 里写了 `permitAll()` 的路径，如果**没同时**加到这个过滤器的白名单里，
请求会先被过滤器拦下返回"授权过期"，`permitAll` 根本不生效。
之前 `/actuator/prometheus` 抓不到数据就是这个原因。

> 面试价值：这道题能区分"会配 Spring Security"和"理解过滤器链顺序"。
> 你可以说："`permitAll` 是授权规则，过滤器是认证环节，过滤器在授权之前；
> 过滤器短路了，授权规则永远没机会执行。"

### 4.3 租户上下文（`agent/tenant/TenantInterceptor.java`）

```java
Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
if (authentication != null && authentication.isAuthenticated()
        && authentication.getPrincipal() instanceof LoginUser loginUser) {
    Long boundMerchantId = loginUser.getMerchantId();
    if (boundMerchantId != null) {
        TenantContext.setTenantId(boundMerchantId);   // 只信登录态
        return true;
    }
    // 平台管理员才允许用 X-Tenant-Id 显式指定
}
```

改造前是直接从 `X-Tenant-Id` 请求头取——**客户端说自己是哪个租户就是哪个租户**，
这属于典型的水平越权（事故库第 8 条）。现在的规则是：

- 普通商户用户：租户 = JWT 里的 `merchantId`，请求头一律忽略。
- 平台管理员（`merchantId == null`）：才允许用请求头指定。

### 4.4 为什么 Controller 很薄

随便打开一个 Controller 会发现它基本只做三件事：参数接收、调 Service、包 `ResultVo`。
真正的业务在 `service/impl`。这是标准的分层，但你要能说出**它带来的一个具体好处**：

> "库存扣减的原子性必须在 Service 层保证，因为 Controller 可能被多个入口调用
> （后台页面、AI Tool、定时任务）。如果把事务放在 Controller，AI 调用时就漏了。"

## 5. 数据模型：两张订单表，别搞混

这是读代码时第一个容易迷路的地方。

| 实体 | 表 | 含义 | 谁写 |
|------|----|------|------|
| `ShopOrder` | `oms_shop_order` | **平台原始订单**（从淘宝/京东拉下来的） | 拉单服务 |
| `OOrder` | `o_order` | **ERP 内部订单**（审核、发货、售后基于它） | `pushOms` 转换 |
| `ShopRefund` | `oms_shop_refund` | 平台售后单 | 拉单服务 |
| `OGoodsInventory` | `o_goods_inventory` | 库存主表（总库存/锁定/可用） | 库存服务 |
| `OGoodsInventoryOperation` | `o_goods_inventory_operation` | 库存流水（每次变动一条） | `changeStock` |
| `OGoodsInventoryBatch` | `o_goods_inventory_batch` | 批次（FEFO 用） | 入库/出库 |

> 面试问"你们的订单模型"时，答"OMS 原始单 + ERP 内部单双层"，
> 并解释原因："平台字段结构和内部履约字段不一致，原始单保留快照便于对账和重放。"

## 6. 代码规模与"不要看哪里"

很多人学项目失败，是因为从 `open-sdk` 或 `model/entity` 开始读，读了三天还在看平台字段。

**正确的进入顺序**：

```
启动类 → 一个 Controller → 对应 ServiceImpl → 对应 Mapper → 表结构
```

**明确跳过**：

- `open-sdk/**`（251 个文件，全是平台 HTTP 签名与字段映射）。
- `model/**` 里 300 多个实体（用到哪个看哪个）。
- `vue3/**`（前端）。
- 仓库根目录 20 多个 `build*.log`（历史构建垃圾）。

## 7. 本篇自测（合上文档回答）

1. 七个模块的依赖方向是什么？为什么状态机放在 `service` 而不是 `erp-api`？
2. 一次带 JWT 的请求，经过哪些组件？`permitAll` 为什么会被过滤器"架空"？
3. `oms_shop_order` 和 `o_order` 的区别是什么？为什么要两张表？
4. 仓库三个时代的划分依据是什么？为什么"先边界后智能"？
5. 如果面试官问"这是单体还是微服务，为什么"，你怎么答？

### 第 5 题的参考答法

> "是单体多模块。选单体不是技术落后，而是这个业务的现实：订单、库存、采购在同一个事务边界里，
> 拆成微服务就要处理分布式事务；而且团队只有我一个人维护，微服务的运维成本不合理。
> 我用**模块边界**模拟了微服务的隔离：service 不依赖 erp-api，Agent 运行时单独一个包，
> 将来真要把 Agent 拆出去，依赖方向是干净的。"
