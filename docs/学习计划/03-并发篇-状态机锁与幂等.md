## 1. 状态机：把散落的 if/else 收成一张表

### 1.1 改造前的样子（反面教材）

```java
// 散落在 Service / Controller / 前端的判断
if (order.getStatus() == 1 && target == 2) { ... }
else if (order.getStatus() == 2 && target == 3) { ... }
else { throw new RuntimeException("状态不对"); }
```

问题不是"写得丑"，而是：

1. **规则不可枚举**：想知道"待发货能去哪"，得全仓库搜。
2. **校验与执行分离**：校验在这段 if，更新在另一段 SQL，中间可能被改。
3. **无法审计**：跳转没有统一出口，想记录"谁把订单从 1 改成 3"只能靠日志。

### 1.2 现在的实现（`service/.../statemachine/OrderStateMachine.java`）

```java
private static final Map<Integer, Set<Integer>> TRANSITIONS = new HashMap<>();

static {
    addTransition(0, 21, 1, 11, 12);
    addTransition(21, 1, 11, 13);
    addTransition(1, 2, 101, 11, 12);
    addTransition(101, 2, 12);
    addTransition(2, 3, 12);
    addTransition(3, 12);
    addTransition(12, 3, 13, 11, 1, 2);
    addTransition(22, 1, 11);
}

public static boolean canTransition(Integer fromState, Integer toState) {
    if (fromState == null || toState == null) return false;
    if (fromState.equals(toState)) return true;   // 幂等：同状态视为合法
    Set<Integer> allowed = TRANSITIONS.get(fromState);
    return allowed != null && allowed.contains(toState);
}
```

状态编码（必须记住几个常用的）：

| 码 | 含义 | 码 | 含义 |
|----|------|----|------|
| 0 | 新订单 | 11 | 已取消 |
| 1 | 待发货 | 12 | 退款中 |
| 2 | 已发货 | 13 | 已关闭 |
| 3 | 已完成 | 21 | 待付款 |
| 101 | 部分发货 | 22 | 锁定 |

**迁移图（这张要能默画）**：

```
0 新订单 ──┬──► 21 待付款 ──► 1 待发货 ──► 2 已发货 ──► 3 已完成
           ├──► 1 待发货          │            │
           ├──► 11 已取消         ├──► 101 部分发货 ──► 2
           └──► 12 退款中         ├──► 11 已取消
                                  └──► 12 退款中
12 退款中 ──► 3 / 13 / 11 / 1 / 2
22 锁定   ──► 1 / 11
```

注意：箭头表示**合法迁移**，不代表业务一定这么走。
比如 `12 → 1`（退款中回到待发货）是"退款被拒/撤销"的场景，不是常规路径。

### 1.3 为什么用"表"而不是"枚举 + switch"

- 表是**数据**，可以打印、可以画图、可以给前端做"下一步可选动作"。
- 新增状态只改一行 `addTransition`，不改控制流。
- 可以写成单测遍历所有 `(from, to)` 组合，验证没有遗漏。

> 面试话术：
> "状态机不是'更优雅的 if'，它把**规则**从**流程**里抽出来了。
> 抽出来之后，规则可以被测试、被展示、被审计。"

### 1.4 售后状态机（`RefundStateMachine.java`）

```java
static {
    addTransition(0, 2, 1, 8);      // 申请 → 处理中/关闭/平台处理中
    addTransition(2, 3, 6, 5, 1, 8);// 处理中 → 退款中/待买家发货/待用户处理/关闭
    addTransition(6, 2, 1);         // 待买家发货 → 处理中/关闭
    addTransition(5, 2, 1);         // 待用户处理 → 处理中/关闭
    addTransition(3, 4, 1, 2);      // 退款中 → 成功/关闭/处理中
    addTransition(8, 2, 3, 1, 4);   // 平台处理中 → ...
}
```

注意 `2 → 3`（处理中 → 退款中）这条边：工作流里就是先 `0 → 2`，再 `2 → 3`，
**不能一步 `0 → 3`**。这是"状态机与业务实际行为对齐"的修复点（事故库第 9 条）。

## 2. 校验器：校验 + 发事件（`TransitionValidator.java`）

```java
public void validateOrderTransition(Integer fromState, Integer toState, String orderId) {
    boolean allowed = OrderStateMachine.canTransition(fromState, toState);
    publish("ORDER", orderId, fromState, toState,
            OrderStateMachine.getStateName(fromState),
            OrderStateMachine.getStateName(toState), allowed);
    if (!allowed) {
        throw new IllegalTransitionException("订单状态非法迁移: ...");
    }
}
```

两个设计意图：

1. **统一出口**：所有状态变更前都调它，非法迁移直接抛异常。
2. **事件驱动审计**：无论通过还是拦截，都发 `StateTransitionEvent`，由
   `StateTransitionTraceListener` 写入 Trace。状态机与监控解耦。

### 2.1 这里有一个值得主动讲的"不完美"

`StateTransitionTraceListener` 用 `REQUIRES_NEW` 开独立事务写 Trace：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onApplicationEvent(StateTransitionEvent event) { ... }
```

后果：**校验通过时就已经写了一条"迁移成功"的 Trace**，如果后面的业务更新失败回滚，
Trace 里仍然留着"成功"的记录。

> 面试官如果追问"你的审计可靠吗"，正确的答法是：
> "状态迁移的审计是'意图审计'，不是'结果审计'。真正的事实审计在 `ActionLedger`
> 和库存流水里——那两张表与业务同事务，回滚就一起回滚。
> 这是我后来才想清楚的分层：Trace 记链路，Ledger 记结果。"

## 3. 乐观锁：`@Version` 到底保护了什么

### 3.1 机制

`MybatisPlusConfig` 注册了 `OptimisticLockerInnerInterceptor`：

```java
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
```

实体上有 `@Version` 的字段（`ShopOrder.version`、`ShopRefund.version`、`OGoodsInventory.version`）
在 `updateById(entity)` 时会被改写成：

```sql
UPDATE oms_shop_order
SET seller_memo = ?, version = version + 1
WHERE id = ? AND version = ?
```

`affected = 0` 表示版本冲突，调用方应重试或报错。

### 3.2 三个必要条件（缺一不可）

1. 实体字段有 `@Version`；
2. 走 `updateById(entity)` 或 `update(entity, wrapper)`，**不是**自定义 SQL；
3. 传入的 `version` 不为 null（这就是为什么代码里要 `update.setVersion(existing.getVersion())`）。

### 3.3 哪些路径"绕过"了它（这是高分点）

| 路径 | 是否走乐观锁 | 说明 |
|------|-------------|------|
| `orderService.updateById(update)` + `setVersion` | ✅ | `OrderActionTools` 已按此修复 |
| `OGoodsInventoryMapper.deductStockAtomic` | ❌ 原生 SQL | 但 SQL 里手写了 `version = version + 1`，属于"手工维护版本" |
| `LambdaUpdateWrapper` 直接 update | ❌ | 不会自动加 version 条件 |
| `ErpPurchaseOrder` | ❌ | 实体至今没有 `@Version`，迁移加了列但代码没用 |

> 面试话术（非常重要）：
> "乐观锁不是加了注解就万事大吉。它只保护 `updateById` 这一条路径。
> 我的库存扣减用的是原生 SQL，所以我在 SQL 里手动 `version = version + 1`，
> 保证'版本一定前进'；但我不依赖它做并发控制——并发控制靠的是 `WHERE quantity >= ?` 的条件更新。
> version 在这里的作用是**给增量同步和排查提供变更序号**，不是锁。"

这段话能同时展示"知道机制"和"知道边界"，比背"乐观锁是 CAS"强得多。

### 3.4 为什么还需要分布式锁

乐观锁解决"同一行并发更新"，但解决不了：

- **跨多行的事务**（先查 A 再改 B，中间被别人插队）；
- **非数据库资源**（调用外部接口、生成唯一单号）；
- **重复执行**（同一请求被两个实例同时处理）。

所以三者是分层的：

```
幂等键   → 防"同一件事做两次"        （业务语义层）
分布式锁 → 防"两个实例同时做"        （实例协调层）
乐观锁   → 防"两次更新互相覆盖"      （数据行层）
```

## 4. 分布式锁：Redisson 的正确用法与坑

### 4.1 实现（`agent/gateway/DistributedLockService.java`）

```java
public LockHandle tryLock(String lockKey, long ttlSeconds) {
    RLock rlock = redissonClient.getLock(LOCK_PREFIX + lockKey);
    boolean acquired = rlock.tryLock(0, ttlSeconds, TimeUnit.SECONDS);
    return acquired ? new LockHandle(key, rlock, true)
                    : new LockHandle(key, null, false);
}
```

Redisson 帮你处理了：

- **可重入**：同一线程重复加锁不会死锁（Hash 结构记录 `threadId:count`）。
- **释放校验**：解锁时校验持有线程，避免 A 超时后删了 B 的锁。
- **原子性**：加锁/解锁都是 Lua 脚本。

### 4.2 一个必须知道的细节：看门狗什么时候生效

Redisson 的 watchdog 只在**没有显式指定 `leaseTime`** 时启动
（`tryLock()` 或 `tryLock(waitTime, TimeUnit)`）。
上面代码传了 `ttlSeconds`，等于**关闭了自动续期**：任务跑超过 TTL，锁会提前释放。

> 面试可以主动说：
> "我们这里显式给了 30 秒 leaseTime，所以没有 watchdog 续期。
> 对短事务够用；如果是长任务，应该用不带 leaseTime 的重载，让 Redisson 每 10 秒续一次。
> 这是一个已知的取舍，不是没想到。"

### 4.3 内存锁的经典 bug（事故库第 6 条）

`ToolGateway` 早期版本：

```java
} finally {
    executionLocks.remove(toolName);   // 无条件删
}
```

场景：

1. 线程 A 拿到锁，正在执行；
2. 线程 B 调 `acquireLock` 失败，抛异常；
3. B 的 `finally` 把 A 的锁删了；
4. 线程 C 成功加锁，与 A **并发执行**。

修复：加一个 `inMemoryLockAcquired` 标记，只有真正拿到锁的线程才释放。

```java
boolean inMemoryLockAcquired = false;
...
if (!acquireLock(toolName)) throw ...;
inMemoryLockAcquired = true;
...
} finally {
    if (inMemoryLockAcquired) executionLocks.remove(toolName);
}
```

> 这是"锁必须由持有者释放"的最小反例，面试讲这个比讲 AQS 源码更可信。

## 5. 幂等：三个层次，别混为一谈

### 5.1 HTTP/接口层

同一请求重复提交（用户连点、网关重试）。常见做法是前端防抖 + 后端 token。
本项目在 AI 工具层用 Redis 做（见下）。

### 5.2 工具调用层（`agent/gateway/IdempotencyGuard.java`）

```java
Boolean acquired = redisTemplate.opsForValue().setIfAbsent(
        key, STATUS_PROCESSING, keyGenerator.getTtlSeconds(), TimeUnit.SECONDS);
if (Boolean.FALSE.equals(acquired)) {
    String existing = redisTemplate.opsForValue().get(key);
    if (existing != null && existing.startsWith(STATUS_COMPLETED)) {
        return IdempotencyResult.duplicate(cachedResult);   // 直接返回上次结果摘要
    }
    return IdempotencyResult.processing();                  // 正在执行，拒绝
}
return IdempotencyResult.proceed(key);
```

关键点：

- **`SET NX` 是原子的**。早期版本是 `GET` 再 `SET`，两个并发请求都能通过检查（事故库第 7 条）。
- 状态机：`processing → completed:{result}`，失败时删除 key 允许重试。
- Redis 不可用时 **fail-open**（放行 + 告警），避免 Redis 故障阻塞所有写操作。

> 面试追问："fail-open 不会导致重复写吗？"
> 答："会，但这是有意的取舍：Redis 全挂时，可用性优先于幂等。
> 真正的兜底在数据库唯一索引（库存流水）和业务状态机（重复取消会被状态机拦住）。"

### 5.3 数据层（最强保证）

`o_goods_inventory_operation` 上的 `uk_operation_idempotency` 唯一索引：

```java
try {
    writeOperation(cmd, inv, before, after);
} catch (DuplicateKeyException e) {
    throw new ServiceException("库存流水幂等键冲突，本次操作已回滚");
}
```

应用层的 `selectCount` 只是"快速路径"，**唯一索引才是最终裁决**。

## 6. 并发怎么验证：不要只说"我加了锁"

`erp-api/src/test/.../InventoryConcurrencyTest.java` 用 50 个线程直连 MySQL 扣同一行库存，
断言：

- 成功次数 × 每次扣减量 = 实际扣减总量；
- 库存不为负；
- 流水条数 = 成功次数。

压测入口 `BenchmarkController` 走的是**与生产完全一致的 `changeStock` 链路**，
不是绕过 Service 直接打 SQL。

> 面试话术：
> "验证并发不能靠'我觉得加了锁就没事'。我的用例是 50 线程抢同一行，
> 断言三个不变量：不超卖、不为负、流水条数对得上。
> 这条用例必须连真实 MySQL——H2 的行锁语义不一样，测了等于没测。"

## 7. 本篇自测

1. 画出订单状态迁移图（至少包含 0/1/2/3/11/12/21/101）。
2. 为什么 `0 → 2` 不合法，但 `0 → 21 → 1 → 2` 合法？这反映了什么业务约束？
3. `@Version` 生效的三个条件是什么？原生 SQL 更新时它还有用吗？
4. 分布式锁的 watchdog 在什么条件下生效？显式 leaseTime 有什么风险？
5. 幂等的三层分别防什么？为什么说唯一索引才是最终裁决？
6. 如果面试官问"你的锁会不会死锁"，怎么答？

### 第 6 题的参考答法

> "三种情况要考虑：一是进程崩溃，Redisson 的锁有 TTL，到期自动释放；
> 二是业务超时，leaseTime 到期释放，但任务可能还在跑——所以长任务要么续期、要么把 TTL 设得足够大；
> 三是锁顺序，我们只对单个工具名加锁，不会出现 A 等 B、B 等 A 的环路。
> 真正的死锁风险在数据库行锁，那要靠统一加锁顺序（比如库存按 id 升序扣）来避免。"
