# 02 业务篇：订单主线与库存一致性

> 目标：能完整讲出"一张采购单怎么变成库存"，以及"为什么这样扣库存不会超卖"。
> 预计用时：D2 全天 + D3 上午（约 6 小时）

---

## 1. 先看全局：四条业务主线

| 主线 | 入口 | 关键表 | 终点 |
|------|------|--------|------|
| 订单 | `ShopPullApiServiceImpl.pullOrder` | `oms_shop_order` → `o_order` | 发货 / 售后 |
| 采购 | `ErpPurchaseOrderController` | `erp_purchase_order` → `erp_stock_in` | 库存增加 |
| 出库 | `ErpStockOutController` | `erp_stock_out` → `o_goods_inventory` | 库存减少 |
| 售后 | `ShopRefundController` | `oms_shop_refund` → `o_refund` | 退款 / 退货入库 |

**学习顺序建议**：采购入库 → 出库 → 订单 → 售后。
原因：入库是"库存增加"的最短闭环，出库是它的镜像，订单只是触发源，售后最复杂（涉及状态机 + 逆向库存）。

## 2. 订单主线：平台适配器 + 状态映射

## 3. 采购入库：一张单如何变成库存

### 3.1 链路（这张图要能默画）

```
采购单(erp_purchase_order)
   │ 收货
   ▼
入库单(erp_stock_in) ──► 入库明细(erp_stock_in_item)
   │
   │ 确认入库 applyStockIn()
   ▼
┌──────────────────────────────────────────────┐
│ OGoodsInventoryService.changeStock(cmd)       │   ← 唯一入口（@Transactional）
│                                              │
│ ① 幂等前置：流水表查 idempotency_key          │
│ ② 原子更新：UPDATE ... WHERE quantity >= ?    │   ← InnoDB 行锁
│ ③ 回读余额：SELECT（同事务，读到自己的写）      │
│ ④ 写流水：INSERT o_goods_inventory_operation  │   ← 唯一索引兜底
└──────────────────────────────────────────────┘
   │
   ├──► o_goods_inventory（总库存/可用库存 +n，version+1）
   └──► o_goods_inventory_batch（批次，FEFO 用）
```

### 3.2 关键代码（`service/.../impl/ErpStockInServiceImpl.java`）

先看"新库存记录怎么建"：

```java
if (invList.isEmpty()) {
    OGoodsInventory inv = new OGoodsInventory();
    inv.setWarehouseId(request.getWarehouseId());
    inv.setMerchantId(stockInItem.getMerchantId());
    inv.setSkuId(Long.parseLong(stockInItem.getSkuId()));
    // 余额由流水驱动：新库存记录从 0 起算，入库量通过 changeStock 记账，
    // 保证"每一分库存都有对应流水"，对账才有账可对
    inv.setQuantity(0);
    inv.setLockedQuantity(0);
    inv.setAvailableQuantity(0);
    oGoodsInventoryService.save(inv);
    goodsInventoryId = inv.getId();
}
applyStockIn(goodsInventoryId, item.getIntoQuantity(), erpStockIn, stockInItem, userName);
```

**这段注释是全项目最值钱的一句话**：
改造前是 `inv.setQuantity(qty)` 直接写——库存"凭空出现"，没有流水。
现在新记录从 0 开始，所有增加都走 `changeStock`，于是**任何一分库存都能在流水里找到来源**。

再看 `applyStockIn`：

```java
private void applyStockIn(Long inventoryId, Integer qty, ErpStockIn stockIn,
                          ErpStockInItem item, String userName) {
    InventoryChangeCommand cmd = InventoryChangeCommand.of(inventoryId, qty,
            InventoryChangeCommand.TYPE_IN);
    cmd.setBizType(stockIn.getStockInType() == 2
            ? InventoryChangeCommand.BIZ_RETURN_IN       // 退货入库
            : InventoryChangeCommand.BIZ_PURCHASE_IN);   // 采购入库
    cmd.setBizId(stockIn.getId());
    cmd.setBizNum(stockIn.getStockInNum());
    cmd.setBizItemId(item.getId());
    cmd.setMerchantId(stockIn.getMerchantId());
    cmd.setOperator(userName);
    int accumulated = (item.getInQuantity() == null ? 0 : item.getInQuantity()) + qty;
    cmd.setIdempotencyKey("IN_ITEM:" + item.getId() + ":" + accumulated);
    if (!oGoodsInventoryService.changeStock(cmd)) {
        throw new ServiceException("增加库存失败：库存记录 " + inventoryId);
    }
}
```

四个设计点，面试要能逐条讲：

1. **Command 对象**：把"变多少"和"为什么变"绑在一起，流水天然带业务单号。
2. **bizType 区分来源**：采购入库 vs 退货入库，对账时能分开统计。
3. **幂等键格式** `IN_ITEM:{明细ID}:{累计入库量}`：同一个明细重复提交同一累计量，只会记一次账。
4. **失败抛异常**：`changeStock` 返回 false 表示库存记录不存在/条件不满足，必须中断整个事务，
   不能像改造前那样"丢弃返回值继续走"。

## 4. 库存三量模型：这是所有讨论的基础

`OGoodsInventory` 有三个数量字段：

| 字段 | 含义 | 谁改 |
|------|------|------|
| `quantity` | 总库存（物理在库） | 入库 +、出库 -、盘点调整 |
| `locked_quantity` | 已锁定（下单未发货） | 锁定 +、解锁 -、出库时扣减 |
| `available_quantity` | 可用库存 | 入库 +、锁定 -、解锁 +、出库 - |

不变式：**`available = quantity - locked`**（正常情况下）。

三种典型操作对三量的影响：

| 操作 | quantity | locked | available |
|------|----------|--------|-----------|
| 入库 | +n | — | +n |
| 锁定（下单） | — | +n | -n |
| 解锁（取消） | — | -n | +n |
| 出库（发货） | -n | — | -n |

> 面试陷阱：有人会说"出库应该同时减 locked"。在这个模型里，出库前如果已经锁定，
> 正确的做法是先"解锁"再"出库"，或者出库时同时扣 locked。**看代码**：
> `deductStockAtomic` 只减 `quantity` 和 `available`，不减 `locked`。
>
> **但要注意一个事实**：当前主流程（`ErpStockOutServiceImpl`）并没有调用 `lockStock`，
> 锁定量只在对账/盘点场景被检查。也就是说，正常出库时 `locked = 0`、`available = quantity`，
> 不会出问题；一旦将来启用"下单锁库存"，出库前必须先解锁，否则 `available` 会被扣两次。
> 这是一个**可以主动指出的设计约束**，面试官会认为你真的读懂了模型，而不是背了三量关系。

## 5. 核心：`changeStock` 四步

文件：`service/.../impl/OGoodsInventoryServiceImpl.java`

```java
@Override
@Transactional(rollbackFor = Exception.class)
public boolean changeStock(InventoryChangeCommand cmd) {
    String invalid = cmd.validate();
    if (invalid != null) throw new ServiceException(invalid);

    // 1. 幂等前置校验
    if (cmd.getIdempotencyKey() != null && !cmd.getIdempotencyKey().isEmpty()) {
        Long existing = operationMapper.selectCount(
                new LambdaQueryWrapper<OGoodsInventoryOperation>()
                        .eq(OGoodsInventoryOperation::getIdempotencyKey, cmd.getIdempotencyKey()));
        if (existing != null && existing > 0) {
            return true;   // 已记过账，直接成功
        }
    }

    // 2. 条件原子更新
    int affected = switch (cmd.getType()) {
        case InventoryChangeCommand.TYPE_IN     -> baseMapper.addStockAtomic(inventoryId, quantity);
        case InventoryChangeCommand.TYPE_OUT    -> baseMapper.deductStockAtomic(inventoryId, quantity);
        case InventoryChangeCommand.TYPE_LOCK   -> baseMapper.lockStockAtomic(inventoryId, quantity);
        case InventoryChangeCommand.TYPE_UNLOCK -> baseMapper.unlockStockAtomic(inventoryId, quantity);
        case InventoryChangeCommand.TYPE_ADJUST -> baseMapper.adjustQtyAtomic(inventoryId, quantity);
        default -> 0;
    };
    if (affected == 0) return false;

    // 3. 回读变动后余额
    OGoodsInventory inv = this.getById(inventoryId);

    // 4. 同事务写流水
    int delta = switch (cmd.getType()) {
        case TYPE_IN -> quantity;
        case TYPE_OUT -> -quantity;
        case TYPE_ADJUST -> quantity;
        default -> 0;   // 锁定/解锁不改总库存
    };
    try {
        writeOperation(cmd, inv, inv.getQuantity() - delta, inv.getQuantity());
    } catch (DuplicateKeyException e) {
        throw new ServiceException("库存流水幂等键冲突，本次操作已回滚：" + cmd.getIdempotencyKey());
    }
    return true;
}
```

### 5.1 为什么第 3 步"回读"是安全的（高频追问）

面试官会问："你 UPDATE 完又 SELECT，中间不会被别人改吗？"

答：

> "不会。第 2 步的 UPDATE 已经对目标行加了排他锁（InnoDB 行锁），
> 而且事务还没提交。其他事务想改这一行必须等锁释放。
> 所以第 3 步在**同一个事务**里读到的，一定是我这次 UPDATE 之后的值。
> 这不是'多查一次'，是用行锁换确定性——有了它，我不需要 `SELECT ... FOR UPDATE`，
> 也不需要额外快照就能精确算出 `before_qty = after_qty - delta`。"

### 5.2 为什么"先查后写"会超卖

改造前的写法：

```java
OGoodsInventory inv = getById(id);
if (inv.getQuantity() >= qty) {          // T1 读到 10
    inv.setQuantity(inv.getQuantity() - qty);
    updateById(inv);                     // T2 也读到 10，两个都扣，最终 8 而不是 0
}
```

两个线程同时读到 10，都判断"够"，都扣 5，结果库存变成 0 但卖了 10 件。
改成一条 SQL：

```sql
UPDATE o_goods_inventory
SET quantity = quantity - #{quantity},
    available_quantity = available_quantity - #{quantity},
    version = version + 1
WHERE id = #{id}
  AND is_delete = 0
  AND quantity >= #{quantity}
  AND available_quantity >= #{quantity}
```

`WHERE` 里的判断和 `SET` 里的扣减在**同一条语句、同一个执行计划**里完成，
InnoDB 会对匹配行加锁后再求值，第二个事务要么等待、要么 `affected = 0`。这就是"条件原子更新"。

### 5.3 为什么还要 `available_quantity >= ?`

这是审查报告里指出的 P1 缺陷：早期版本只校验 `quantity >= ?`，
当有锁定量时，`available` 会被扣成负数。

举例：`quantity=10, locked=8, available=2`，出库 5。
只校验 `quantity` 会通过，结果 `quantity=5, available=-3`——账面上"有货"，实际可用是负的。

修复后两个条件都校验，`affected=0`，业务层收到 false 后抛异常回滚。

> 面试价值：这是"能说出一个自己修过的真实 bug"的好素材，比背八股强十倍。

### 5.4 幂等的两道保险

| 层 | 机制 | 防什么 |
|----|------|--------|
| 应用层 | 先 `selectCount(idempotencyKey)` | 正常重试（网络超时后客户端重发） |
| 数据库层 | `uk_operation_idempotency` 唯一索引 | 并发重试（两个事务同时通过了前置校验） |

第二层才是真正的保证：先提交者插入成功，后提交者 `DuplicateKeyException`，
被 catch 后抛 `ServiceException`，**整个事务回滚**——库存不动、流水不重复。

> 面试追问："如果先查后插之间有人插了怎么办？"
> 答："唯一索引会拦住，我捕获 `DuplicateKeyException` 后回滚，不会出现'库存扣了两次'。"

## 6. 出库：批次 + 总库存双扣

`ErpStockOutServiceImpl.applyStockOut` 与入库镜像：

```java
InventoryChangeCommand cmd = InventoryChangeCommand.of(inventoryId, qty,
        InventoryChangeCommand.TYPE_OUT);
if (batch != null) {
    cmd.setBatchId(batch.getId());
    cmd.setBatchNum(batch.getBatchNum());
}
cmd.setBizType(outBizType(outItem.getType()));
cmd.setBizId(outItem.getEntryId());
cmd.setBizNum(outItem.getSourceOrderNum());
int accumulated = (outItem.getOutQuantity() == null ? 0 : outItem.getOutQuantity()) + qty;
cmd.setIdempotencyKey("OUT_ITEM:" + outItem.getId() + ":" + accumulated);
if (!oGoodsInventoryService.changeStock(cmd)) {
    throw new ServiceException("总库存不足，出库失败");
}
```

批次扣减也是原子 SQL：

```sql
UPDATE o_goods_inventory_batch
SET current_qty = current_qty - ?
WHERE id = ? AND current_qty >= ?
```

改造前是 `getById` 判断 + `updateById` 写回，并发下同一批次会被重复扣（批次级超卖）。

> FEFO（先到期先出）：批次按 `id` 升序取（最早入库的先出）。
> 代码里在 `rebalanceBatches` 的注释明确写了"采用与出库 FEFO 一致的顺序"。

## 7. 对账：发现差异，但不"改总库存"

文件：`service/.../impl/StockReconcileServiceImpl.java`

### 7.1 核心原则（背下来）

> **总库存是事实，账（流水）与明细（批次）向它靠拢。**
> 对账只负责发现并记录差异；补偿只调整流水和批次，**绝不凭空改总库存**。

这句话是整个模块的设计哲学，也是面试最能加分的一句。

### 7.2 五类差异（`StockReconcileDiff`）

| 类型 | 含义 | 能不能自动补偿 |
|------|------|----------------|
| `TYPE_AVAILABLE_MISMATCH = 1` | `available ≠ quantity - locked` | 能（按公式重算） |
| `TYPE_BATCH_MISMATCH = 2` | 批次合计 ≠ 总库存 | 能（按 FEFO 调批次） |
| `TYPE_BOOK_ACTUAL_MISMATCH = 3` | 流水推算余额 ≠ 实际库存 | 能（补一条调整流水） |
| `TYPE_NEGATIVE_OR_OVERLOCK = 4` | 负库存 / 超锁 | **不能**，需人工盘点 |
| `TYPE_FLOW_CHAIN_BROKEN = 5` | 流水链断裂（前后余额接不上） | **不能**，需逐笔核对 |

### 7.3 对账主流程

```java
while (true) {
    IPage<OGoodsInventory> page = inventoryMapper.selectPage(new Page<>(pageNo, BATCH_SIZE), qw);
    if (page.getRecords().isEmpty()) break;
    checkBatch(page.getRecords(), report);   // 五项校验
    if (pageNo >= page.getPages()) break;
    pageNo++;
}
```

三个工程细节：

1. **分批扫描**：不一次性 `select *`，避免大表 OOM。
2. **批量取汇总**：一次取这一批的流水汇总和批次汇总，避免 N+1。
3. **差异去重**：同一库存同一类型已有 PENDING 差异就不再插入，避免每日对账刷屏。

### 7.4 补偿代码的关键分支

```java
switch (diff.getDiffType()) {
    case TYPE_AVAILABLE_MISMATCH -> ...
    case TYPE_BATCH_MISMATCH     -> rebalanceBatches(inv, target, operator);
    case TYPE_BOOK_ACTUAL_MISMATCH -> writeReconcileFlow(inv, bookQty, delta, diff, operator);
    case TYPE_NEGATIVE_OR_OVERLOCK ->
            throw new ServiceException("负库存/超锁属于事实异常，需盘点后人工调整，不支持自动补偿");
    case TYPE_FLOW_CHAIN_BROKEN ->
            throw new ServiceException("流水链断裂需逐笔核对流水，不支持自动补偿");
}
```

**"哪些能自动修、哪些必须人工"** 是这道题的得分点：
能自动修的是"派生数据"（可用量、批次、流水），不能自动修的是"事实异常"（负库存、链断裂）。

## 8. 本篇自测

1. 画一张"采购入库 → 库存 → 流水 → 批次"的时序图。
2. `changeStock` 四步分别解决什么问题？去掉任何一步会怎样？
3. 为什么回读不会读到脏数据？如果用 `READ COMMITTED` 隔离级别还成立吗？
4. 幂等的两层保险分别防什么场景？
5. 对账的五类差异，哪两类不能自动补偿，为什么？
6. 出库时 `deductStockAtomic` 不减 `locked`，调用方要注意什么？

### 第 3 题的加分答法

> "成立，但依赖行锁而不是隔离级别。UPDATE 持有排他锁到事务结束，
> 回读在同一事务内，读到的是自己写后的值（read-your-own-writes）。
> 如果换成 `SELECT ... FOR UPDATE` 也一样；真正不能省的是'更新与回读必须在同一事务'。"

### 第 6 题的答法

> "当前主流程没有启用锁定量——`lockStock` 只有定义、没有调用方，所以 `locked=0`，
> `available=quantity`，出库只扣两个字段是自洽的。
> 但如果将来做'下单锁库存'，出库前必须先解锁，否则 `available` 会被扣两次。
> 这不是当前 bug，是模型留下的约束，我在读代码时特意确认过调用链。"
