### 1.2 为什么是这个顺序（面试可讲的三条原则）

**原则一：先能启动，再谈能力。**
10-13 之前，项目"类都齐了但起不来"：PgVector 饿汉、Redisson 不兼容、Lombok 全局崩。
所以第一批修复全是"让应用能跑"。

**原则二：先堵越权，再谈智能。**
Agent 能查全租户订单、能用请求头伪造租户、审批接口谁都能批——
这些不修，功能越多越危险。

**原则三：先有评测，再谈优化。**
RAG 的 Recall/MRR 是在 10-17 才真实可信的。在此之前所有"效果很好"都是感觉。

> 面试话术：
> "我不是按'功能清单'推进的，是按'风险'推进的。
> 每周先问：现在最可能让系统崩/泄密/背锅的是什么？先修那个。"

## 2. 六个必须会讲的事故（详细版）

### 事故 1：一个泛型，让 98 个类的 Lombok 全部失效

**现象**：`erp-api` 编译报 200 个错，全是"找不到 `log`""找不到 `getXxx()`""找不到 `builder()`"，
看起来像 Lombok 没生效，但依赖明明在。

**定位**：错误集中指向 `R.java`。它是 `public class R extends HashMap<String, Object>`（无泛型），
而新代码写了 `R<List<ActionLedger>>`、`R<Page<ActionLedger>>`。

**根因**：javac 在解析"无泛型类被参数化使用"时类型解析异常，
**触发 Lombok 注解处理器全局中止**。Lombok 一停，所有 `@Data/@Slf4j/@Builder` 的生成方法全部消失。

**修复**：给 `R.java` 加标准泛型 `<T>`，所有静态方法返回 `R<T>`。

**验证**：clean compile 通过；确认 `ActionLedger$ActionLedgerBuilder.class` 存在。

> 面试讲法（30 秒）：
> "最迷惑的是报错信息和根因完全无关——200 个 Lombok 错误，真正的问题在一个返回体类少了泛型。
> 这件事让我以后看到'批量注解失效'先怀疑注解处理器，而不是逐个类去查。"

---

### 事故 2：Redisson 在 Spring Boot 4.1 下无法启动

**现象**：引入 `redisson-spring-boot-starter:3.35.0` 后启动失败，
报找不到 `RedisProperties`。

**根因**：Redisson 3.35 是针对 Boot 3.x 编译的，引用了 Boot 4 已移除的类；
而项目代码其实**完全没用到 Redisson**（当时锁是手写的）。

**修复**：从 pom 和 `application-agent.yml` 移除 Redisson；
后来需要分布式锁时，改用 `RedissonClient` 的**独立配置**（`RedissonConfig` 手动构建），
不再依赖 starter 的自动装配。

**教训**：第三方 starter 的兼容性要看它编译时依赖的 Boot 版本，不是看它声明的版本范围。

> 面试可延伸："为什么后来又把 Redisson 加回来？"
> 答："因为手写 `SET NX + UUID + Lua 解锁` 容易漏边界（误删、续期、可重入）。
> 自己写一遍是为了理解，生产用成熟库是为了正确。"

---

### 事故 3：PgVector 饿汉 Bean，让"三级降级"变成空话

**现象**：没装 PostgreSQL 的机器上，应用启动直接失败；
文档里写的"PG 不可用降级到 MySQL/BM25"完全走不到。

**根因**：`PgVectorManualConfig` 里 `PgVectorStore` 是饿汉 Bean，
`afterPropertiesSet()` 会执行 `CREATE EXTENSION vector` + 建表。
PG 不通 → Bean 初始化抛异常 → 整个 Spring 上下文起不来。

**修复**（两步）：

1. 启动类排除官方自动配置：

```java
@SpringBootApplication(excludeName = {
    "org.springframework.ai.vectorstore.pgvector.autoconfigure.PgVectorStoreAutoConfiguration"
})
```

2. 手动配置加开关 `agent.vector-store.enabled`，关闭时**根本不创建** `PgVectorStore` Bean，
   `PgVectorRetriever` 注入为 null，`HybridRetriever` 自然走第二级。

**验证**：`AGENT_VECTOR_STORE_ENABLED=false` 启动成功，日志显示降级；
`=true` 时连接 pgvector，建表校验通过。

> 面试话术：
> "降级链不是写了 if 就行。第一级的 Bean 如果在启动时就强制初始化，
> 后面的降级代码永远执行不到。**降级的前提是'允许第一级不存在'**。"

---

### 事故 4：迁移脚本互相打架，干净库必然失败

**现象**：按序号执行 `db/migration` 下的脚本，报 `Unknown column 'merchant_id'`；
换个顺序又报建表冲突。

**根因**（三个叠加）：

1. 仓库没有任何迁移执行器（无 Flyway/Liquibase），脚本靠人工执行；
2. `agent_rag_evaluation` 有三套定义：V1_11 建的列和 V1_16/V1_22 用的列不一致，
   `CREATE TABLE IF NOT EXISTS` 静默跳过，不会补列；
3. `agent_memory` 同样有两套语义不同的定义。

**修复**：

- 接入 Flyway（`baseline-on-migrate: true`，允许在已有库上建基线）；
- 新增 `V1_30_0__real_rag_evaluation.sql` 统一评测表结构；
- 手工改过结构的库要在 `flyway_schema_history` 登记版本，否则重启会重复执行。

**验证**：干净库（官方 145 张表 dump）+ 全部 V1 脚本按序执行成功；
`rag_document` / `agent_rag_evaluation` 各 100 条。

> 面试话术：
> "`CREATE TABLE IF NOT EXISTS` 是迁移脚本里最危险的写法——
> 它让'表已存在但结构不对'静默通过。迁移要做的是**版本化变更**，不是'确保表存在'。"

### 事故 5：审批功能"看起来有"，但永远执行不了

这是最有代表性的一个，因为它由**五个小问题叠加**而成：

| # | 问题 | 后果 |
|---|------|------|
| 1 | `ChatService` 硬编码 `approved=false` | 永远认为"未审批" |
| 2 | traceId 每次对话 `UUID.randomUUID()` | 批准后重发带新 traceId，匹配不上旧审批 |
| 3 | `ChatService` 没把 `OrderActionTools` 传给 ChatClient | 写工具根本不能被 AI 调用 |
| 4 | `ApprovalController.getById` 用 `listByTraceId("")` 再过滤 | 永远 404 |
| 5 | `expireOldApprovals()` 没有 `@Scheduled` | 5 分钟超时形同虚设，PENDING 永久堆积 |

**修复**：

1. traceId 提升到 session 级：`String traceId = sessionId != null ? sessionId : UUID...`；
2. `OrderActionTools` 注入 ChatService 的工具列表；
3. 审批查询改为 `selectById`；
4. `expireOldApprovals` 加 `@Scheduled`；
5. 审批通过后执行成功要 `markExecuted`，失败回 `PENDING` 并清审批人。

**验证**：`ApprovalServiceTest` + 端到端手工验证"发起取消 → 生成审批 → 批准 → 重发 → 执行成功"。

> 面试讲法（这段最能体现工程能力）：
> "单个 bug 好修，难的是'链路断在五个地方'。
> 我的定位方法是**沿着一次真实请求走一遍**：从用户点发送，到工具执行，到数据库落库，
> 每一步打印关键字段（traceId、approvalId、status），哪一步断了立刻能看出来。
> 最后发现不是审批逻辑错，是**身份（traceId）在每一轮都变了**。"

### 事故 6：网关的锁，被没拿到锁的线程删了

**现象**：并发测试时，标了 `allowConcurrent=false` 的工具仍然并发执行。

**根因**：

```java
} finally {
    executionLocks.remove(toolName);   // 无条件删
}
```

B 线程抢锁失败 → 抛异常 → `finally` 把 A 持有的锁删了 → C 线程立刻拿到锁，与 A 并发。

**修复**：加 `inMemoryLockAcquired` 标记，只有真正拿到的线程才释放。

**验证**：`ToolGatewayTest` 并发用例；以及代码 review 时逐个检查"锁的获取与释放是否成对"。

> 面试话术：
> "锁的释放必须由持有者完成，这是分布式锁和本地锁的共同规则。
> 我后来在 Redisson 那边也确认了同样的语义：解锁会校验持有线程。"

## 3. 九个简版事故（每个 30 秒能讲完）

### 事故 7：幂等的 GET-then-SET 竞态

- **现象**：并发重复提交仍会执行两次。
- **根因**：`GET` 判断不存在 → `SET`，两步之间被另一个请求插入。
- **修复**：`setIfAbsent`（`SET NX`）原子化；值用 `processing` / `completed:{result}` 区分状态。
- **一句话**："幂等标记必须是原子的，检查与占位不能分两步。"

### 事故 8：租户隔离是"客户端说了算"

- **现象**：不带 `X-Tenant-Id` 就能查到所有商户订单。
- **根因**：拦截器直接从请求头取租户；工具层 `if (merchantId != null)` 才过滤。
- **修复**：租户只从登录态（`LoginUser.merchantId`）取；工具网关 fail-closed；管理接口从登录态取商户。
- **一句话**："租户是身份属性，不是请求参数。"

### 事故 9：状态机校验的迁移，业务根本没执行

- **现象**：工作流对大多数订单直接失败；或校验通过但订单状态没变。
- **根因**：
  1. `validate_transition` 校验"当前状态 → 3（已完成）"，但状态机只允许 `2→3`；
  2. 全程没有真正更新订单状态，只改了退款状态和备注；
  3. 仓库里有两套状态机（`statemachine` 与 `service.statemachine`），语义分叉。
- **修复**：状态机下沉到 `service`；工作流先 `→12（退款中）` 再处理；删除重复实现；
  用 `TransitionValidator` 统一校验并发事件。
- **一句话**："校验的规则必须和实际写入的规则是同一套，否则校验只是表演。"

### 事故 10：DAG 的"断点续跑"是 no-op

- **现象**：调用 `resumeWorkflow` 什么都不执行。
- **根因**：只在全部结束后保存一次快照，快照里所有节点都是终态；
  `while (!isAllCompleted())` 直接为假。
- **修复**：节点完成即保存 checkpoint；`execute` 恢复时保留已有状态；
  `saveCheckpoint` 加 `synchronized` 解决 `MAX(version)+1` 竞态。
- **一句话**："恢复能力的前提是'中途有状态可恢复'，不是'最后存一份'。"

### 事故 11：Actuator 白名单被过滤器架空

- **现象**：`/actuator/prometheus` 返回"授权过期"，Prometheus 抓不到数据。
- **根因**：`SecurityConfig` 写了 `permitAll`，但 `JwtAuthenticationTokenFilter`
  对不在自己白名单里的请求直接短路返回 JSON。过滤器在授权之前。
- **修复**：过滤器白名单补 `/actuator/health`、`/actuator/prometheus`。
- **一句话**："`permitAll` 是授权规则，过滤器是认证环节；认证短路，授权永远没机会执行。"

### 事故 12：RAG 评测"自欺"

- **现象**：评测报告一片绿，线上答非所问。
- **根因**：
  1. 向量检索返回硬编码 chunk；
  2. 生成答案是"拼接前 3 个 chunk"；
  3. BLEU/ROUGE 用同一个 Jaccard，中文按空格切；
  4. 评测集标注的 chunk 在真实库里不存在。
- **修复**：评测集对齐真实 `sop_*`；接真实 LLM 生成与裁判；标准 BLEU-4/ROUGE-L；
  `LLM_STRICT` 模式失败即终止；报告标注 `LLM/HEURISTIC`。
- **一句话**："指标低不可怕，指标假才可怕。评测必须能失败。"

### 事故 13：记忆系统没有预算，也没有清理

- **现象**：长会话越来越慢、越来越贵；Redis 出现慢查询。
- **根因**：三层记忆全量拼进 SystemMessage；`listKeys` 用 `KEYS`；
  `WORKING` 内存 Map 无淘汰；每轮写新 key 无上限。
- **修复**：每层 450 字符预算、倒序截断；`SCAN` 替代 `KEYS`；定时清理过期；
  会话历史 20 条 / 6000 字符。
- **一句话**："记忆不是越多越好，上下文是有限预算，要像内存一样管理。"

### 事故 14：库存"扣了但不知道为谁扣"

- **现象**：出库成功但账面没扣；流水只有"扣 5 个"，查不到订单。
- **根因**：
  1. 调用方丢弃 `deductStock` 返回值；
  2. 流水 `bizType` 硬编码、`bizId=0`；
  3. 批次扣减先查后写，并发重复扣；
  4. 新库存直接 `setQuantity(qty)`，没有流水。
- **修复**：统一 `changeStock` + `InventoryChangeCommand`；条件原子 SQL；同事务写流水；
  批次原子扣减；新记录从 0 起算。
- **一句话**："库存的每一次变动都必须能回答三个问题：变了多少、为什么变、凭什么说变对了。"

### 事故 15：测试在干净机器上必然失败

- **现象**：`mvn test` 在别人电脑上全红。
- **根因**：14 个测试硬编码 `127.0.0.1:3306` + `root/1234`，直接读写业务库；
  没有 `@SpringBootTest`，Bean 装配从未被验证。
- **修复**：集成测试打 `@Tag("it")`，默认排除；提供 `integration-tests` / `all-tests` profile；
  CI 用 MySQL/Redis service container；连接参数读环境变量。
- **一句话**："测试不能只在作者机器上绿。要么隔离，要么标注它需要什么。"

## 4. 修复顺序的方法论（面试可讲）

审查报告给的顺序，本质是**按"能不能用"分层**：

```
第 1 层：能启动、能复现
   ↓（否则一切讨论无意义）
第 2 层：堵越权、堵资金/库存损失
   ↓（安全与钱是第一优先级）
第 3 层：打通闭环（审批、写工具、通知）
   ↓（功能"存在"不等于"可用"）
第 4 层：修正确性（锁、幂等、状态机、库存）
   ↓（并发下的正确性）
第 5 层：归口与观测（写路径统一、指标、Trace）
   ↓（可运维）
第 6 层：评测与优化（RAG、记忆、缓存）
```

> 面试话术：
> "我不会按'哪个模块酷'排序，而是按'哪个问题会让系统不可用/不安全/不可信'排序。
> 先让系统能跑，再让它不闯祸，最后才让它变聪明。"

## 5. 怎么把事故讲成故事（模板）

面试讲事故，用这个五段式，控制在 90 秒：

1. **现象**：一句具体的话（"审批通过了但工具不执行"），不要抽象。
2. **定位**：你用了什么手段（"沿一次请求打日志，发现 traceId 每轮都变"）。
3. **根因**：一句话说清机制（"审批匹配键是 traceId，而 traceId 是每次新生成的"）。
4. **修复**：具体动作 + 为什么这么修（"提升到 session 级，因为审批匹配的是'一次意图'而不是'一次请求'"）。
5. **验证/沉淀**：怎么证明修好了 + 留下了什么（"端到端用例 + 把 traceId 生命周期写进注释"）。

**不要做的事**：

- 不要说"AI 生成的代码有问题"——面试官会怀疑你的贡献。
- 不要只说"我改了某某文件"——要说"我判断了什么"。
- 不要编造没修过的 bug——追问两层就露馅。
