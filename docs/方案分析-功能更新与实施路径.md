## 一、方案核心目标

### 1.1 方案定位
**不是重写平台,而是补"运行时治理层"**

方案的核心思想是在已有的启航ERP和现有能力基础上,增加一个**可审计、可恢复、可评测的受限自治层**,使其成为真正的企业级Agent工程系统,而非简单的AI对话助手。

### 1.2 投入权重调整
- **启航 ERP 后端底座**: 45% (订单流转、库存、售后、权限)
- **PaiAgent 运行时与评测**: 35% (工具权限、评测审计、受限RAG、持久化记忆)
- **开源贡献或 MiniAgent**: 20% (可选,优先给活跃项目提PR)

| **记忆系统** | ai_conversation_history表 | ❌ 无分层、无TTL、无隔离 |
| **知识库** | 未实现(PGVector依赖注释) | ❌ 无RAG能力 |

| **5** | **持久化分层记忆** | ⚠️ 单表简陋 | Working/Session/User/Team四层 | 🔧 重构升级 |

#### 🛠️ 启航ERP定向改造

| 改造项 | 当前实现 | 方案要求 | 影响范围 |
|--------|---------|---------|---------|
| **状态机并发安全** | Service层散落更新 | 显式状态迁移表+乐观锁+分布式锁 | 订单/售后Service |
| **ERP工具网关** | 直接调用Service | 租户投影+权限检查+读写分级+审批 | 所有AI Tool类 |

| **多租户隔离** | merchant_id存在但未强制 | 强制注入+查询过滤+审计 | 所有数据访问层 |

## 六、风险点与应对策略

### 6.1 技术风险

| 风险 | 影响 | 应对 |
|------|------|------|

## 十、常见问题FAQ

### Q1: 为什么不直接用Spring State Machine?
**A**: Spring State Machine适合单一状态机定义,但启航ERP有多个业务实体(订单、售后、库存)各有状态迁移规则。方案采用**自定义状态迁移表+TransitionValidator**,可以:
- 为不同实体定义独立状态机
- 动态加载状态迁移规则(支持配置化)
- 与ActionLedger审计深度集成
- 避免Spring State Machine的复杂配置

### Q2: PGVector部署困难怎么办?
**A**: 提供**三级Fallback方案**:
1. **优先**: Docker部署pgvector (官方镜像 `ankane/pgvector`)
2. **备选**: MySQL全文索引 + MATCH AGAINST (性能降低但可用)
3. **最小**: 内存cosine全表扫描 (仅适合<1000条文档)

### Q3: 方案会影响现有订单流程吗?
**A**: **不会直接影响**。改造采用**灰度发布策略**:
- 保留原有OrderService接口不变
- ToolGateway作为新入口,旧流程继续走原Service
- 状态机校验可配置开关 `agent.statemachine.enabled=true`
- 分阶段切流: 先只读Tool → 再低风险写Tool → 最后高风险Tool

### Q4: ActionLedger会影响性能吗?
**A**: 采用**异步写入+批量刷盘**:
```java
@Async("actionLedgerExecutor")
public void logAction(ActionLedgerEntry entry) {
    // 写入内存队列
    ledgerQueue.offer(entry);
    // 每500ms或100条批量flush到MySQL
}
```
- 对主流程性能影响<5ms
- 定时任务清理30天前审计数据

### Q5: 如何验证方案实施效果?
**A**: **三个关键指标**:
1. **Tool调用成功率** ≥ 95% (Grafana实时监控)
2. **RAG Recall@10** ≥ 0.8 (离线评测集)
3. **并发状态更新冲突率** < 1% (压测100并发)

## 十二、关键决策点记录

### 决策1: 为什么不重写PaiAgent?
**理由**: 
- PaiAgent的DAG拓扑排序、GraphBuilder已经正确实现
- 重写风险高,工期不可控
- **补运行时治理层**比重写性价比更高
- 保留原有工作流编排能力,只增强受限自治、审计、评测

### 决策2: 为什么先做ERP后端,再做Agent运行时?
**理由**:
- 启航ERP是业务数据底座,不稳定则Agent无用武之地
- 状态机、并发控制、租户隔离是**生产必备**,不是Demo功能
- 先保证后端45%投入,再分配Agent运行时35%
- 避免"Agent花哨但订单流转出Bug"的失衡

### 决策3: 为什么RAG和记忆优先于DAG并行?
**理由**:
- RAG是企业Agent的**核心能力差异点**(对话式AI的基础)
- 持久化记忆影响用户体验(用户说"我叫张三",下次记得)
- 并行DAG是**性能优化**,不影响功能正确性
- 有限时间先保证功能完整,再优化性能

### 决策4: 为什么ActionLedger是必做项,而Checkpoint是可选?
**理由**:
- ActionLedger是**合规与审计要求**(谁操作了什么、能否回滚)
- Checkpoint是工作流恢复能力,适用于长流程场景
- 启航ERP大部分操作是**短流程**(查询订单、创建采购单),Checkpoint收益低
- 优先保证操作可追溯,再考虑流程可恢复

## 十三、总结

### 方案核心价值
本改进方案**不是泛化包装或简单增加节点类型**,而是在已有启航ERP和PaiAgent基础上,补齐了**企业级Agent工程的可信执行边界**:

1. ✅ **受限自治层** - Agent不能绕过Policy直接操作数据
2. ✅ **审计与回溯** - 每一笔操作都有ActionLedger记录
3. ✅ **多租户隔离** - 跨租户数据不可见,租户A看不到租户B订单
4. ✅ **状态机约束** - 禁止非法状态跳转(如待发货→已完成)
5. ✅ **并发安全** - 乐观锁+分布式锁解决库存扣减竞态
6. ✅ **评测闭环** - RAG有评测集,Tool有成功率,不是"能跑就行"
7. ✅ **分层记忆** - Working/Session/User/Team四层,有TTL和隔离

### 与"泛化包装"的本质区别

| 维度 | 泛化包装(低价值) | 本方案(高价值) |
|------|----------------|--------------|
| **数据库** | "支持145张表" | 订单状态机+乐观锁+幂等键 |
| **AI Tool** | "接入了11个工具" | ToolGateway+Policy分级+ActionLedger审计 |
| **记忆** | "保存聊天记录" | 四层分级+TTL+租户隔离+敏感脱敏 |
| **RAG** | "能回答问题" | 混合检索+引用+100条评测集+离线回归 |
| **并发** | "支持多线程" | 确定性并行+失败传播+取消策略+Checkpoint |

### 可讲深的技术亮点
面试官追问时,可深入讲解:

**Q: ToolGateway如何防止Prompt注入诱导工具执行?**
A: Policy + Approval双重检查:即使AI被诱导调用"取消订单",ToolGateway检查到`requiresApproval=true`,会触发人工确认弹窗,不直接执行。

**Q: 并行DAG如何保证结果确定性?**
A: 保留原始拓扑序作为基线,并行结果与串行结果可比较。无依赖节点并行时,最终全局变量合并顺序按nodeId排序,不依赖线程调度顺序。

**Q: RAG评测集如何构建?**
A: 三步法:
1. 从真实客服对话中抽取100个典型问题
2. 人工标注期望召回的chunk_id
3. 每次改动跑离线评测,Recall@10/MRR/Faithfulness,保留历史指标对比

**Q: 状态机如何与ActionLedger集成?**
A: 状态迁移前记录`before_state`,迁移后记录`after_state`+`transition_reason`。如果操作失败,根据ActionLedger的`compensation_method`字段自动执行反向迁移(如"已发货"→"待发货"需回滚物流信息)。
