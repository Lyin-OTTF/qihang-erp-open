# 库存流水闭环与定时对账 — 实现说明

本文对应审计报告中的两处缺口：

1. 「库存流水：条件原子更新 + 同事务生成流水 + 定时对账」只有查询工具，没有扣减重构、流水补全与对账任务；
2. 仓库内无压测脚本（`benchmark/stress/jmeter` 全部搜不到）。

改造后，这两条能力都有可直接运行、可验证的代码与数据支撑。

---

## 一、改造前的问题（为什么不能只"补个定时任务"）

| 现状 | 后果 |
|------|------|
| `ErpStockOutServiceImpl.stockOut()` 调用 `deductStock(...)` **丢弃返回值** | 库存不足时业务继续往下走 → 出库单成功、账面没扣 → 账实不符 |
| `OGoodsInventoryBatchServiceImpl.deductBatchStock()` 是 `getById` 判断 + `updateById` 写回 | 并发出库同一批次被重复扣减（批次级超卖） |
| 流水 `bizType` 硬编码 `4/90`、`bizId=0`、`bizNum=""` | 流水只知道"扣了 5 个"，不知道"为哪张单扣的"，无法追溯、无法对账 |
| 流水无 `merchant_id` | 多租户下无法按商户对账，跨租户混账 |
| 流水无变动前后余额、无幂等键 | 重试会重复记账；对账缺少链式校验的锚点 |
| 全库无对账任务 | 账实差异只能等人工发现 |

结论：**先修流水，再谈对账**。流水本身不可追溯，对账任务只会把脏数据固化成每日告警。

## 二、库存变动：单一入口 + 条件原子更新 + 同事务流水

### 2.1 统一入口 `changeStock(InventoryChangeCommand)`

`InventoryChangeCommand` 把"扣多少"和"为什么扣"绑在一起：库存ID、数量、变动类型、业务类型、业务单号/明细、
商户、操作人、幂等键。旧的三参数接口保留并委托到新入口，调用方无需一次性全量迁移。

执行顺序（`OGoodsInventoryServiceImpl#changeStock`）：

```
① 幂等前置校验  → 幂等键已存在则直接返回成功（库存只动一次）
② 条件原子更新  → UPDATE ... WHERE quantity >= ? AND available_quantity >= ? AND is_delete = 0
③ 同事务回读    → UPDATE 持有行锁且事务未提交，回读必为本次写入后的余额
④ 同事务写流水  → before = after ∓ qty，写失败整笔回滚
```

关于 ③：这一步看起来像"多查一次"，实际是**用行锁换取确定性**。因为 ② 已在目标行上加排他锁且未提交，
其他事务无法修改该行，所以 ③ 读到的 `quantity` 必然是本次操作后的值，`before_qty` 可由 `after ∓ qty` 精确反推，
不需要额外快照或 `SELECT ... FOR UPDATE`。

### 2.2 幂等

- 幂等键格式约定：`{动作}:{业务明细ID}:{累计序号}`，例如 `OUT_ITEM:1024:3`（该明细第 3 次累计出库）；
- 表上 `uk_operation_idempotency` 唯一索引兜底：并发下两个事务带同一键时，后提交者插入冲突 → 整笔回滚，
  保证"库存不变、流水不重复"；
- 重试命中前置校验则返回 `true`（视为已成功），业务侧无感知。

### 2.3 批次扣减同样原子化

```sql
-- 之前：先查再写，两步之间可被抢占
SELECT current_qty ... ;  UPDATE o_goods_inventory_batch SET current_qty = ? WHERE id = ?

-- 现在：一条 SQL 完成判断与扣减
UPDATE o_goods_inventory_batch SET current_qty = current_qty - ?
 WHERE id = ? AND current_qty >= ?
```

`ErpStockOutServiceImpl` 中的两条调用路径（指定批次 / FEFO 自动选批）都改为检查返回值，
失败即抛 `ServiceException`，整笔出库事务回滚——不再出现"出库成功但账面没扣"。

### 2.4 入库也走流水

改造前，新建库存记录时直接 `inv.setQuantity(qty)` 写库，相当于"库存凭空出现"，没有任何流水。
现在新记录以 `quantity=0` 建账，再通过 `changeStock(TYPE_IN)` 入账，
保证**每一分库存都有对应流水**，对账才有账可对。

## 三、定时对账

### 3.1 五项校验

| # | 类型 | 校验 | 发现的问题 |
|---|------|------|-----------|
| 1 | `1 可用量不一致` | `available_quantity == quantity - locked_quantity` | 派生列被绕过写坏 |
| 2 | `2 批次合计不一致` | `Σ batch.current_qty == quantity` | 批次与总库存不同步（FEFO 只扣了一边） |
| 3 | `3 账实不一致` | 末笔流水 `after_qty == quantity` | 库存变了但没记账（静默扣减失败） |
| 4 | `4 负库存/超锁` | `quantity>=0 && available>=0 && locked<=quantity` | 事实异常，需盘点 |
| 5 | `5 流水链断裂` | `Σ净额 == 末笔after - 首笔before` | 漏记/重记流水 |

聚合查询用了窗口函数（MySQL 8），一次取回每个库存的净额、首笔 `before`、末笔 `after`，
避免"按库存逐条查流水"的 N+1；库存按 500 条一批分页扫描，单批内一次取流水汇总、一次取批次汇总。

### 3.2 去重与告警

- 同一库存 + 同一差异类型若已有「待处理」记录，本轮不再新增 → 每日对账不会把同一问题刷成 N 条；
- 差异落 `o_stock_reconcile_diff`，任务结束按报告发告警：站内消息 `sys_message` + 外部渠道
  （`NotifierService`：飞书/钉钉/企业微信，取决于 `sys_alert_channel` 配置）；
- 对账任务自身异常也会告警——否则"定时任务静默失败"会让差异长期无人发现。

### 3.3 补偿语义：只调账，不凭空改库存

这是设计上最关键的取舍：**总库存是事实，账与明细向它靠拢**。

| 差异类型 | 补偿动作 | 为什么不直接改 `quantity` |
|---------|---------|--------------------------|
| 可用量不一致 | 重算 `available = quantity - locked` | 派生列错误，重算即可，不涉及实物 |
| 批次合计不一致 | 差额按 FEFO 顺序回填/扣减到批次 | 批次是明细账，总库存才是事实 |
| 账实不一致 | 补记一条 `type=5` 调整流水（`before`=末笔after，`after`=quantity） | 实物已经动了，缺的是账；补账而非改库存 |
| 负库存/超锁 | **拒绝自动补偿**，提示盘点 | 事实本身异常，自动"修"只会掩盖问题 |
| 流水链断裂 | 拒绝自动补偿，需逐笔核对 | 无法判断哪一笔错了，改了就是伪造流水 |

补偿必须逐条人工确认（`POST /compensate/{diffId}`），不做批量自动修复，避免把真实库存问题静默抹平。

### 3.4 定时与开关

```yaml
erp:
  stock:
    reconcile:
      enabled: true          # 本地调试可关
      cron: "0 10 3 * * ?"   # 每日 03:10，业务低峰
```

任务：`cn.qihangerp.erp.job.StockReconcileJob`。

## 四、接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/erp-api/stockReconcile/diffs?status=&merchantId=` | 差异列表（分页） |
| POST | `/api/erp-api/stockReconcile/run?merchantId=` | 手工触发对账，返回报告 |
| POST | `/api/erp-api/stockReconcile/compensate/{id}` | 人工确认后补偿 |
| POST | `/api/erp-api/stockReconcile/ignore/{id}` | 忽略差异 |
