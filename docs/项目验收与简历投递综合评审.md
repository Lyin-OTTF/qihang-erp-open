## 八、MiniAgent 具体应该怎么写（方向建议，暂不动手）

**定位**：一个"证明你理解 Agent 运行时底层"的最小内核，不是为了再做一个框架。核心是**用 500–800 行讲清一个完整闭环，而不是 1200 行摊薄成四个半成品**。

### 8.1 建议聚焦一个主线：ReAct 循环 + 工具调用 + HITL 中断续跑

```
用户输入 → Agent Loop（终止条件 + 最大步数 + 预算）
        → 工具 Schema 注册（name/description/jsonSchema 校验）
        → Function Calling 参数解析（LLM 返回 JSON → 反序列化 → 校验必填/类型）
        → 副作用记录（每次工具调用前落 "intent log"）
        → 幂等键（工具名 + 参数摘要哈希 → 去重）
        → Checkpoint 快照（每步后序列化 state → 可恢复）
        → HITL：高危工具先挂起 → 人工 approve → resume 不重放副作用
```

### 8.2 核心组件（每个都小而可测）

| 组件 | 关键点 | 面试追问点 |
|------|--------|-----------|
| `AgentLoop` | 终止条件设计（最大迭代 / 模型显式 finish / 连续无工具调用 N 次 / token 预算） | 为什么不用 while(true)？如何防死循环？ |
| `ToolRegistry` | 工具 Schema 注册 + 参数 JSON Schema 校验（用 Jackson 校验必填/类型/枚举） | 非法参数在哪一层拦？ |
| `FunctionCallParser` | LLM 结构化输出 → 反序列化 + 严格校验，失败重试或降级 | 模型返回脏 JSON 怎么办？ |
| `SideEffectLog` | 每次写操作前先记录 intent（操作类型/目标/入参摘要） | 为什么要"先记后做"？ |
| `IdempotencyGuard` | 幂等键 = hash(toolName + 参数)，SETNX 语义 | 与"副作用记录"是什么关系？ |
| `CheckpointStore` | 每步后序列化 state（内存 map 即可，不必上 Redis） | 哪些对象不能序列化？ |
| `HITL` | 高危工具 → 挂起 → 恢复时从 checkpoint 续跑，跳过已执行副作用 | 恢复时怎么"不重放"？ |

### 8.3 最小可交付形态（2–3 天）

- 单模块 Maven/纯 Java，无第三方 Agent 框架（对得上简历"自研运行时"）
- 一个 `main` 跑通：`查询订单 → 触发取消订单(高危) → 挂起 → 人工批准 → 从 checkpoint 续跑 → 输出最终结果`，并打印"未重放副作用"的证据
- 10–15 个单元测试覆盖：循环终止、Schema 校验、参数解析、幂等、checkpoint 恢复、HITL 不重放

**为什么不建议现在写 1200 行**：面试官要的是"你能讲清一个闭环的设计权衡"，不是行数。一个 600 行、每个组件都有测试、且能演示 HITL 不重放副作用的内核，比 1200 行四不像强得多。写完后再回填简历的"约 600–800 行"即可。
