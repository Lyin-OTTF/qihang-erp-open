## 二·补、23:00 复检新增：两项遗留问题已闭环，可写进简历

### A. 定时对账闭环（原"差一步成立"的 claim 现在成立）

**已交付**：`StockReconcileJob`（`@Scheduled(cron = "${erp.stock.reconcile.cron:0 10 3 * * ?}")`，默认每日 03:10，`erp.stock.reconcile.enabled` 可关）+ `StockReconcileController`（`/diffs` `/run` `/compensate/{id}` `/ignore/{id}`）。

**细节到位的地方**（这些是面试可以展开的）：
- 差异去重：同一库存 + 同一差异类型已有待处理记录时不再堆积，避免每日对账刷屏；
- 告警分级：差异 >10 条标 `high`，否则 `warning`；先写站内消息，再走 `NotifierService` 多渠道；
- **失败也告警**：对账任务自身异常会推"库存对账任务执行失败"，避免定时任务静默失败；
- 补偿语义克制：可用量/批次/账实可自动补，负库存与流水链断裂**直接抛异常要求人工处理**，不自动改库。

**验证**：`StockReconcileServiceTest` 4/4 通过（可用量、批次、账实、负库存不自动补偿）；`InventoryConcurrencyTest` 3/3 通过。

**结论**：第三节 ② 的"定时对账 + 告警"可以正式写回，措辞见第五节。

### B. 压测资产与真实基准（原"详见仓库压测脚本"现在有据可查）

**已交付**：`benchmark/` 共 13 个文件——Java 基准入口 + k6 脚本（`cache-compare.js` / `stock-deduct.js`）+ JMeter（`.jmx`）+ 造数与校验 SQL + 运行脚本（sh/ps1）+ 两份真实报告。

**可直接引用的数据**：

| 场景 | 数据 | 含义 |
|------|------|------|
| 缓存 · 模糊搜索 | P50 **9.04 ms → 0.25 ms（36.8×）** | 省掉 20000 行全表扫描 |
| 缓存 · 主键点查 | P50 **0.12 ms → 0.25 ms（反而慢 0.13 ms）** | 一次 Redis 往返盖过 MySQL 主键查询 |
| 库存扣减 · 旧实现 | 成功 12800 次，**实际只减 424，丢更新 12376** | 等价于超卖 |
| 库存扣减 · 条件原子更新 | 成功 6400 / 库存不足 6400，**丢更新 0** | 32 线程 × 400 次，不超卖 |
| 幂等开销 | 吞吐差 <5% | 一次唯一索引回查可忽略 |

**为什么这组数据比"优化了缓存"值钱**：它包含一个**负结果**——用数据证明"点查不该加缓存"，并据此只缓存搜索与详情。面试官听到"我测完发现缓存更慢，所以改了方案"，比听"我加了缓存提升了性能"可信度高一个量级。这是本次增补里**性价比最高的一句话**。

### ② "定时对账任务生成账实差异记录并告警，人工确认后补偿" —— ✅ 已由另一窗口补齐，claim 成立

**23:00 复检**：`StockReconcileJob` 已挂 `@Scheduled`（默认 03:10，cron 与开关均可配），差异 >0 时写站内消息并走 `NotifierService` 多渠道告警，任务异常也告警；`StockReconcileController` 提供差异列表 / 手工触发 / 补偿 / 忽略四个接口；4 个对账用例 + 3 个并发用例全绿。

**可直接写**：`定时对账任务（默认每日 03:10）生成账实差异记录并按级别告警，人工确认后补偿；负库存与流水链断裂不自动改库`。

> 唯一要守住的分寸：补偿是"以实存为准补流水"，不是凭空改库存。这个边界在 `StockReconcileServiceImpl` 里是硬性抛异常实现的，被追问时可当场指出。

**顺带提醒（23:00 复查结论不变）**：`MessageScheduler.run()` 里六个巡检方法（`checkSalesZero` / `checkShipPending` / `checkRefundExcess` / `checkStockLow` / `checkOrderTimeout` / `checkAiAnalysis`）**仍全部被注释**，`checkStockLow`、`checkOrderTimeout` 内还是 TODO。只有 `retryFailedNotify`（10 分钟周期）在真实运行。**不要写"6 类业务巡检"**。

切分要点：对账调度在独立的 `erp/job/StockReconcileJob`，与上面这组注释掉的消息巡检不是一回事，写对账不会牵出这个坑。

订单 / 售后状态机：在上游订单 / 售后状态枚举基础上，将散落的 if/else 状态判断重构为显式合法迁移表；version 乐观锁防同状态并发覆盖、Redisson 分布式锁护跨实例临界区、幂等键防重复提交与网络重试，三者分层各司其职；并发下单与重复提交经多组用例验证无状态错乱、重复请求被拦截，状态流转可审计；以 251 个单测（43 个测试类）与 25 个 Flyway 迁移保证可回归、可升级；

多租户与 RBAC：在上游 JWT / RBAC 基础上，补齐 Agent Tool 的租户投影与跨租户校验，接口层拦截器与工具调用层双重校验且失败即拒绝（fail-closed），以跨租户越权测试用例验证拦截生效；

通知与实时消息：以单张消息表统一承载站内通知，提供未读 / 已读 / 重试接口；SSE 按 clientId 定向推送与广播，30 秒心跳保活并清理断连；飞书 / 钉钉（加签）/ 企业微信三渠道 webhook 由渠道表配置驱动，推送结果回写状态，失败消息按 10 分钟周期自动重试；

Redis 缓存层：新增热点商品与基础字典缓存（搜索 5 分钟 / 详情 10 分钟 TTL + 主动失效）；以 k6 / JMeter 做命中前后基准，模糊搜索 P50 由 9.04 ms 降至 0.25 ms（36.8×），而主键点查反而慢 0.13 ms，据此只缓存搜索与详情、不缓存强一致点查；

对话式业务 Agent 与工具网关：将商品 / 库存 / 订单 / 售后 / 采购 / 物流 / 会员 / 供应商 / 仓库 / 库存流水 / 补货建议等 14 个工具类的 17 个 @Tool 方法统一经工具网关接入，按五级自主度判定 + 审批单 + 审计账本管控写操作；RAG 侧 BM25 + MySQL 全文 + PgVector 三路召回、RRF 融合后全量 Rerank，99 条真实用例评测 Recall@10 0.9343；
