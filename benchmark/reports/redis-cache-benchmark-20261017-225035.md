# Redis 缓存命中前后响应时间对比

> 生成时间：2026-10-17 22:50:35
> 探针表 20000 行（InnoDB，主键 id + 无索引 payload）；点查 3000 次、搜索 200 次，均含预热

| 场景 | 链路 | 平均(ms) | P50(ms) | P95(ms) | P99(ms) | Max(ms) |
|------|------|---------|---------|---------|---------|---------|
| A 主键点查 | 命中缓存（Redis GET） | 0.26 | 0.25 | 0.39 | 0.56 | 1.19 |
| A 主键点查 | 直连 DB（主键查询） | 0.13 | 0.12 | 0.26 | 0.39 | 0.79 |
| B 模糊搜索 | 命中缓存（Redis GET） | 0.27 | 0.25 | 0.46 | 0.68 | 0.71 |
| B 模糊搜索 | 直连 DB（全表扫描 LIKE） | 9.53 | 9.04 | 13.27 | 15.43 | 16.84 |

## 结论

- **主键点查：缓存 P50 比直连 DB 慢 0.13 ms**（0.25 ms vs 0.12 ms）。一次 Redis 网络往返盖过了 MySQL 主键查询的成本，这类读不应加缓存。
- **模糊搜索：缓存 P50 比直连 DB 快 8.79 ms（9.04 / 0.25 ≈ 36.2 倍）**（0.25 ms vs 9.04 ms）。省掉的是 20000 行全表扫描，这才是缓存的收益来源。
- 因此 `GoodsCacheService` 只缓存搜索与详情结果（5~10 分钟 TTL），而不缓存库存等强一致且点查廉价的数据，是有依据的取舍。

> 局限：本机 loopback 下 Redis 往返约 0.2~0.3ms，跨机房会放大到毫秒级；数据量、索引设计、MySQL 缓冲池命中率都会改变绝对值。结论只对「查询形态的相对关系」负责。
